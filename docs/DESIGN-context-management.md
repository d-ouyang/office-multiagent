# 上下文管理模块 · 重新设计（v2.4.2 提案）

> 2026-11-18 · 触发事故：会话 `s-e499d391c1c73389` 第二轮追问「需要」失忆
> 状态：待评审。本文档取代 `orchestration/memory.py` 现有的 `prepare_turn` 设计。

## 一、现状诊断（先承认问题）

### 1.1 现行实现

`memory.compress_rounds()`：

```python
q = question.replace("\n", " ")[:cap]      # cap = history_round_chars = 80
a = answer.replace("\n", " ")[:cap]
lines.append(f"问：{q} 答：{a}")
```

**这是纯切片**，不是压缩：不总结、不保留结论、不加省略号。

`prepare_turn()` 的分块：

| 块 | 真实来源 | 实际行为 |
| -- | -------- | -------- |
| 【历史摘要】 | `rounds[:-4]` | **同样是 80 字切片**——块名与行为不符 |
| 【近期对话】 | 最近 4 轮 | 每轮 80 字切片 |
| 【指代】 | 代码里写死的代词表 | 只在含「这个/那个/它/刚才」时注入 |
| 【本轮问题】 | 当前文本 | 全量 |

### 1.2 事故还原（真实数据）

会话 `s-e499d391c1c73389`，第二轮用户只说「需要」：

```
【近期对话】最近几轮原文要点。
用户：统计最近两个月各城市、各月份的销售额，画一张城市×月份的热力图
助手：已按你的需求拉数并画好热力图。下面先说口径，再给结论。 **数据口径** - 数据源：锅圈订单库…- 时
用户：需要
助手：任务已暂停，等待补充输入。
【本轮问题】
需要
```

上一轮助手回答 **730 字**，被切成 80 字，**结尾「需要我把这份热力图+分析导出成文档吗」不在上下文里**；
再加上「需要」不在代词白名单、planner 只读 `body.text`，最终判成 general/闲聊 → ask_user 反问要什么。

**结论：多轮对话能力在第二轮即失效，`round_chars=80` 是产品级缺陷，不是调参问题。**

### 1.3 为什么会写成这样

推测动机是"省 token 成本 + 早期小窗口模型的保守策略"。但方向错了：

- **对话文本是廉价的**：4 轮 × 1000 字 = 4000 字 ≈ 4000 token，占比不到 1M 窗口的 0.4%；
- **真正需要压缩的是工具观察**（单步 5 万字表格/文档）——那部分 2.3.0 已经单独处理了；
- 用"截断对话"去省 token，等于为了省 0.4% 的成本砍掉 100% 的指代能力。

### 1.4 相关事实（回答"有没有上限"）

| 项 | 实际值 | 说明 |
| -- | ------ | ---- |
| 单次输出上限 | **8192 tokens**（≈ 6000~8000 汉字） | `TaskTokenBudget.reserve_call(desired_output_tokens=8192)`，再取 `min(8192, 剩余预算−prompt)` |
| 模型上下文窗口 | 由模型决定（deepseek-v4 系 1M、qwen 256K） | 会话总文本远不到窗口上限 |
| 4 轮对话的占比 | ≈ 0.4% | 完全没有压缩的必要 |

## 二、设计目标

1. **近 N 轮对话保持原文**，不截断（默认 N=8，可配）；
2. 更早的轮次用**LLM 增量摘要**（保留结论、数字、决策、未决问题），而非切片；
3. 短确认句（需要/好的/可以/继续）能**消解指代**，对齐到上一轮的具体提问；
4. 整体**按 token 预算分配**，超预算时按优先级从低到高裁剪（先丢最老的整轮，再压摘要，最后才动近期对话）；
5. 每次拼装结果**可回放**（落库 + 事件），用于排障与验收。

## 三、分层模型

```
┌─ L0 系统提示词（Agent 角色 + JSON 协议）        固定，不可压
├─ L1 长期记忆（user_memory：偏好/显式记住的事）  固定，≤ 2K 字符
├─ L2 产物索引（上一轮 clean_id / 文件 / export_id） ≤ 2K 字符
├─ L3 会话摘要（LLM 增量摘要，结构化）            预算 30%
├─ L4 近期对话（最近 N 轮原文）                   预算 55%
├─ L5 本轮问题（含附件引用）                      全量，不压
└─ 预留输出（max_tokens 8192）
```

裁剪顺序（超预算时）：L4 最老整轮 → L3 摘要二次压缩 → L4 更近轮次（最后才动）。

**关键原则：丢整轮，不切半句。** 半句话比没有更危险（模型会把断句当完整意思）。

## 四、预算算法

```
W  = 模型窗口 tokens（models.yaml 声明，如 1_000_000）
O  = 8192                      # 输出预留
S  = 2000                      # 安全边际（协议/工具清单抖动）
C  = min(W, task_token_hard_limit) - O - S   # 可用输入预算

L4_budget = C * 0.55
L3_budget = C * 0.30
其余（L0/L1/L2/L5）= 剩余
```

实现为纯函数 `plan_budget(window, task_limit, overrides) -> Budget`，可单测（给定窗口，断言各层配额与裁剪顺序）。

## 五、摘要算法（替代切片）

### 5.1 结构化摘要

每轮结束后产出**一条结构化记录**，而不是一段散文：

```json
{
  "turn": 3,
  "user_intent": "按月×城市看销售额热力图",
  "keys": {
    "metrics": ["sum_pay"],
    "filters": {"date_from": "2026-09-17", "date_to": "2026-11-17"},
    "groups": ["month", "city"],
    "row_count": 66
  },
  "conclusions": ["上海 10 月 30,581 元居首", "安庆 11 月反超 10 月"],
  "artifacts": ["chart_heatmap.png", "分析报告.docx"],
  "open_questions": ["是否导出文档"]
}
```

`open_questions` 是关键——它让下一轮的「需要」有明确指向。

### 5.2 增量更新（不是重写）

- 新轮次结束 → 生成该轮记录 → 追加到 `session_summary.turns`
- 渲染时把最早的若干条**合并**成一段自然语言（合并也走 LLM，输入是结构化记录，输出 ≤ 800 字）
- 避免"每轮重摘要整段历史"的成本随时间线性增长

### 5.3 用哪个模型

- 摘要用**最便宜的小模型**（`model_pool` 里 flash 档），或走本地 Ollama；
- 单次输入 ≤ 2000 字、输出 ≤ 500 字，成本可忽略；
- 摘要失败 → **回落原文切片**（保留现有行为），绝不阻断任务。

## 六、指代改写（解决「需要」失忆）

两步：

1. **短确认句识别**：文本 ∈ {需要, 要, 好, 好的, 可以, 行, 继续, 不用, 不要, 算了} 或长度 < 4 且无动词；
2. **对齐到上一轮提问**：从上一轮助手回答里抽取**最后一个问句**（正则找以「吗/呢/？」结尾的句子，或摘要里的 `open_questions`），把它作为「本轮所指」注入：

```
【指代】用户这句「需要」是在回答你上一轮的提问：「需要我把这份热力图+分析导出成文档吗？」
按此理解执行，不要再反问。
```

比现在的"只在含代词时加一句提示"精确得多。

## 七、数据结构与接口

### 新表 `session_summary`

| 列 | 类型 | 说明 |
| -- | ---- | ---- |
| session_id | varchar(64) PK 部分 | |
| turn_no | int PK 部分 | 轮次 |
| payload | json | 5.1 的结构化记录 |
| rendered | text | 渲染后的自然语言（缓存） |
| created_at | datetime | |

### 新表 `llm_call`（可观测，与 P1 合并）

| 列 | 说明 |
| -- | ---- |
| run_id / step / agent | 定位 |
| model / effort | 模型 |
| messages_json | **实际发送的完整 messages**（手机号脱敏） |
| response_text | 原始输出 |
| prompt_tokens / completion_tokens / cache_hit | 用量 |
| ms | 耗时 |

### 接口

- `GET /api/v1/runs/{run_id}/context` → 返回该 run 每次调用的 messages（脱敏后的原文）+ 拼装分栏
- 管理端任务详情时间轴：用户输入 → planner → 每步（LLM 上下文可展开 / 工具参数 / 工具输出）→ 终答 → 产物

## 八、兼容与迁移

- `prepare_turn` 保留签名，内部改为调用新 `assemble_context()`，行为切换由 `context_engine=v2` 开关控制；
- 旧会话无 `session_summary` → 首轮按 5.1 补齐（懒生成）；
- `history_round_chars` 保留但语义改为"摘要合并后单段上限"（默认 1500）。

## 九、实施计划

| 阶段 | 内容 | 验收 |
| ---- | ---- | ---- |
| P0 | 近 N 轮原文（N=8）+ 短确认句指代改写 + 丢整轮不切句 | 会话里问「需要」能正确续做；连问 3 轮不丢上文 |
| P1 | `session_summary` + 结构化增量摘要 + 预算算法 | 20 轮后摘要仍含第 1 轮结论；token 不随轮次线性涨 |
| P2 | `llm_call` 落库 + `/runs/{id}/context` + 管理端时间轴 | 每次调用可逐字回看 messages |
| P3 | 摘要合并二次压缩 + 预算超限的降级链 | 塞满窗口仍不报错，且最近 2 轮始终完整 |

## 十、参考的业界做法

| 方案 | 核心思想 | 本设计的取舍 |
| ---- | -------- | ------------ |
| LangChain `ConversationSummaryBufferMemory` | 保留最近 N 轮原文 + 更早轮次滚动摘要 | 采用（这正是我们该有的形态） |
| MemGPT / Letta | 分层记忆（主上下文 / 外部存储）+ 自主换入换出 | 采用分层思想，不做"模型自主调度"（对办公场景过重） |
| Claude Code 的 compaction | 上下文快满时把历史压成摘要并继续 | 采用（对应 P3 降级链） |
| OpenAI Assistants 的 thread 截断 | 按 token 预算裁最老消息 | 采用，但改为"丢整轮"而非丢消息 |
| RAG 式长记忆（向量召回历史） | 按相关度召回旧轮次 | **暂不采用**：办公场景连贯性 > 相关性，且引入检索不确定性 |
