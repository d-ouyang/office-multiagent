## 1. read_document 补阅读器

p6.14 已补上 docx、csv、xlsx、json，表格只给表头、行数和前 20 行。扫描件和图片仍未做。

对外仍是一个工具。模型只传文件名，程序按后缀选阅读器，返回同一结构：文件名、字数或行数、正文、是否截断、读法说明。

| 后缀 | 读法 |
| --- | --- |
| md / txt / json | 按文本读。json 先检查能否解析，解析失败如实说明 |
| csv | 表头 + 行数 + 前若干行文本，不把整表塞进上下文 |
| xlsx | 每个工作表：表名、表头、行数、前若干行 |
| docx | 抽段落文本。表格转成文本行。图片不在这一步识读 |
| pdf | 现有 pypdf 抽文字层 |

扫描件和图片先不做进默认路径，按下面两条解决，做的时候再开任务：

- 扫描版 PDF：文字层为空时不要报「内容为空」就结束。说明这是扫描件。下一步二选一：当前模型支持视觉且请求里真的带了图片，就把页图交给模型；否则走 OCR，把识别出的文字交回 `read_document`。
- 图片：见下文「视觉和 OCR」。没有文字层、OCR 也失败时，回答里写明没读到字，不编造画面内容。

## 2. 视觉和 OCR

支持视觉的模型是自己看图，不是先 OCR。当前注册表里只有 DeepSeek V4.1-Flash 标了 `multimodal_input: true`。对话请求目前只发文字，所以即使用这个模型，图片也还没送进去。

规则：

- 选中的模型支持视觉，且这次请求能带图片：把图片放进该轮请求，不经过 OCR。
- 选中的模型不支持视觉：先 OCR，只把识别出的文字给它。
- 两种结果都记一笔：这次是「模型看图」还是「OCR 文本」，方便上下文用量分栏。

## 3. 表格先清洗再分析

已接上 `clean_table` 和 `analyze_table`。分析只接受清洗返回的 clean_id。

清洗会去掉全空行、全空列、重复表头行和完全相同的行，并去掉首尾空白，把 null、N/A、无、- 视为空。指定了关键列时，这些列为空的行会剔除并单独计数。没有指定关键列时不猜、不删。缺失不用平均数填，异常值不删。数字格式有问题只计数。原文件不改。

## 4. 生成文件和图表

p6.16 已能把结论写成 md 或 docx。xlsx、pdf 和图表还没有。

对外一个 `write_document`，用格式参数区分，对内分写作器。和读取对称。

| 格式 | 适合放什么 |
| --- | --- |
| md / docx / pdf | 总结、说明、带来源的结论 |
| csv / xlsx | 表。xlsx 可以带一张由代码画出的图 |
| png | 只放图，图旁仍要有对应的数据表 |

图表不交给模型画。`render_chart` 吃清洗后的表，加上图表类型和字段：

- 折线：时间轴 + 一个或多个数值
- 柱状：类别 + 数值，类别多时用横向
- 饼图：类别少、加起来是整体时才用
- 热力：两个类别轴 + 一个数值

图的数据必须是工具结果，不能由模型填数。文件先写在临时目录，再登记成可下载产物。失败就说没生成，不给假链接。

## 5. 查业务库和销售报表

现在的 `db_query` 是任意只读 SQL，适合探查，不适合作为「查上海某段时间的订单」的正式入口。扩展时加具名查询，不把 SQL 交给模型拼：

- 例：`query_orders(start, end, region, status)`，参数白名单，SQL 写死在代码里。
- 地区、时间、状态对不上列时，返回「没有这个过滤条件」，不猜列名。
- 行数有上限，超出说明被截断。

销售报表分成两层约束：

- 基础要求：时间范围、指标、口径、数据来源、缺失项。模板里缺一项就不能当完成。
- 提问约束：用户额外要的维度（只要上海、不要退款）必须出现在查询参数里，并在报表开头复述。报表中的每个数字都要能对上某次查询结果。

## 6. 知识库检索

`rag_retrieve` 只做一件事：`POST /api/v1/qa/ask`，正文是 `{"question": 问题}`，再把对方返回的答案和来源交给办公模型。混合检索、BM25、RRF、重排、多问题拆分、依据校验都在 RAG 项目里，不在这个工具里。

因此：RAG 服务开着这些开关时，检索质量就是 RAG 那条链路的质量。办公这边保证不了开关开着，也看不到重排分、子问题和依据校验结果。另外两点和 RAG 界面不一致：请求不带会话，指代改写用不上办公对话；身份是服务账号，不是当前登录用户。

要和 RAG 界面同一质量，需要把上述结果带回工具输出，并用当前用户身份调用。不要在办公项目里重写一套检索。

## 7. 复杂任务的步数

单 Agent 的 ReAct 上限是 10 步（`run_react` 的 `max_iterations`）。读文件、清洗、分析、写总结若各算一次工具调用，大约 4 到 8 步，10 步够。中间如果重复读、反复查、再反思一次，10 步会在写文件之前用完，然后只留下一句「已达上限」。

复杂任务不要把上限改成 30。按阶段拆开，每一阶段自己有步数，阶段之间传递清洗后的表或文件，而不是把全文留在对话里：

| 阶段 | 建议步数 |
| --- | --- |
| 读取 | 4 |
| 清洗 | 4 |
| 分析 | 6 |
| 写文件 | 4 |
| 依据核对 | 2 |

现有多 Agent 图里，每个子任务各自有 10 步。缺的是按这条流水线拆子任务，以及上一步的产物交给下一步。

## 8. 上下文分栏和超大文件

每一轮发给模型之前，按块估算并展示，口径对齐「系统提示 / 工具说明 / 规则 / 本轮对话 / 历史摘要 / 文件观察 / 工具结果」：

- 优先用接口返回的 prompt token 数。
- 没有分项时，用同一分词器对每一块估算，并标明是估算。
- 文件观察单独一栏，避免和普通对话混在一起。

2.4 万字是观察进模型的上限（`_summarize_observation` 和 `_render_history`）。工具本身最多返回 5 万字，多出来的在进模型前被丢掉。中文办公文本粗算 1 个汉字约 0.6 到 1 个 token，所以 2.4 万字大约 1.4 万到 2.4 万 token。默认模型窗口 12.8 万，单份文件放得下。每多一步，这份观察会再带一遍，步数一多才会顶满。

超大文件不要加大这个上限。按文件做临时切片，不写入公司知识库：

- 问具体问题时，只取相关切片。
- 要求通读时，先分段摘要，再摘要合并。
- 回答里说明用了哪些部分，没进上下文的部分不假装读过。

会话记忆和自反思：

- 记忆：下一轮提问带上最近几轮问答的摘要，而不是每轮只看当前这句话。摘要单独占一栏。
- 反思：终答写出之后，用工具结果核对论断，最多改一次。核对占用第 7 节里的「依据核对」步数，不另开长循环。
