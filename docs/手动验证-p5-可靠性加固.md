# 手动验证 · P5 可靠性加固（p5.1 ~ p5.4）

> 分支 `feature/2.0.0-p5-reliability`，**未打 tag、未部署**。
> 本文只列**需要真人操作**的验证项；能自动化的故障场景已全部写成测试，不必手动重复。

## 0. 分工：为什么不是全部手动测

| 验证内容 | 谁来验 | 原因 |
| --- | --- | --- |
| 429 / 500 重试后任务能跑完 | **自动化** | 无法让真实模型"按时"返回 429，手动不可复现 |
| DAG 子任务异常隔离 | **自动化** | 工具失败走 `ToolResult(ok=False)` 不抛异常，手动很难制造子任务级崩溃 |
| 工具退避精确时长 | **自动化** | 0.3s 级别无法靠肉眼确认 |
| 跨实例真续跑不重跑 | **自动化** | 需要构造挂起 + 换 checkpointer 实例 |
| **真实 LLM 端到端不回归** | **手动（你）** | 只有真实模型才能暴露协议/流式/汇总的细微变化 |
| **配置项与落盘行为** | **手动（你）** | 涉及 `.env`、容器重启、文件系统 |
| **重试日志可观测性** | **手动（你）** | 需要看真实 backend 日志 |

## A 组 · 真实 LLM 端到端回归（必做）

### A1 单 Agent 正常任务 —— 验证正常链路没被改坏

- **覆盖**：p5.1（重试代码路径改动）、p5.3（工具调用退避缺省值变化）
- **操作**：登录 dev 账号，提问「查一下最近 10 笔订单」。
- **预期**：
  1. 逐字流式输出正常，没有整段蹦出或重复开头；
  2. 工具调用面板正常展开，`query_orders` 一次成功；
  3. **不出现**「模型暂不可用」；
  4. 任务状态 done，无 error 事件。
- **不通过则**：说明重试/退避改动影响了正常路径，优先看 `backend` 日志是否有非预期的重试记录。

### A2 多 Agent 并行任务 —— p5.2 的重点回归

- **覆盖**：p5.2（`_run_subtask_guarded` 包装了串行与并行两条路径）、p5.1 在 multi 非流式路径的表现
- **操作**：提一个多意图任务。⚠️ **问句选择有讲究（2026-11-07 实测修正）**：
  - ~~「清洗销售数据并画出月度趋势图，再生成一份总结报告」~~——已实测：multi 正常拆分、三子任务全 done，但「清洗」无上传文件时子任务**如实拒绝**（正确行为，非回归），汇总官只能报告清洗未开始，A2 的"交付文件清单正确"验不到。测 p5.2 徽章行为可以用它，测完整交付请用下面两句之一：
  - ✅「先查一下报销制度，然后基于这个制度分析销售数据」（已知 multi：rag→analysis 真实交接，不依赖上传文件）。⚠️ 注意（2026-11-07 用户指出）：**报销制度与销售数据没有自然业务关联，这是为凑 rag→analysis 交接机制强行配对的问句**——analysis 子任务用数据库订单数据（不缺数据），rag 子任务按 KB 实际内容如实回答。语义自然的配对（如"提成制度→提成分析"）受限于演示 KB 目前只有 HR 类制度，见 BACKLOG §9/§10（任务中交互澄清 + KB 补销售口径制度）。
  - ✅ 先上传一份带脏数据的 csv，再说「清洗我刚上传的表格并画出月度趋势图，再生成一份总结报告」（全链路交付版）
- **预期**：
  1. planner 拆出多个子任务，层内并行执行；
  2. **每个子任务的 Agent 徽章最终都进入 done**，没有任何一个卡在 running（p5.2 补发了收尾状态）；
  3. 汇总官整合答复正常，交付文件清单正确（用 ✅ 问句时）；
  4. 各子任务之间**终答没有字符级交错**（multi 仍是非流式块状推送，未被改动）。
- **不通过则**：重点看是否有子任务徽章停在 running，或汇总内容重复。
- **2026-11-07 实测留痕**：原问句 API 实跑——决策模型判 multi，cleaning/analysis/report 三子任务全部 done（无卡 running ✅）、汇总官如实整合"清洗需文件"（无编造 ✅）、11319 tok。p5.2 验证点通过；"交付清单"改用 ✅ 问句补验。

## B 组 · 配置项与持久化行为

### B1 sqlite 模式落盘

- **覆盖**：p5.4
- **前置**：`backend/.env` 增加 `CHECKPOINTER_BACKEND=sqlite`，然后 `docker compose restart backend`。
- **操作**：跑任意一个带 token 池的任务（A1 即可）。
- **预期**：
  1. 启动日志出现 `checkpointer 使用 sqlite 持久化：...`；
  2. 生成 `checkpoints.sqlite` 文件且大小 > 0（默认 `data/checkpoints.sqlite`，注意看容器内路径）；
  3. `docker compose restart backend` 之后**文件仍在**（这就是相对 MemorySaver 的核心收益）。
- **⚠️ 明确边界**：本期**只交付存档能力与真续跑函数**，HTTP `/tasks/{id}/resume` **仍是原来的重跑式**。所以这条**不要**去验证"充值后从断点续跑"——那还测不了，属于后续工作包。

### B2 配置回退（回滚演练）

- **操作**：把 `CHECKPOINTER_BACKEND` 改回 `memory` 或整行删除，`restart backend`，重跑 A1。
- **预期**：行为与 P5 之前完全一致；启动日志不再出现 sqlite 字样。
- **意义**：确认缺省路径零变化，这也是本包可以安全上线的前提。

### B3 未知后端 fail-closed

- **操作**：临时设 `CHECKPOINTER_BACKEND=postgres`，`restart backend`，跑 A1。
- **预期**：明确报错「未知 checkpointer_backend」，**不是**静默回落到 memory 继续跑。
- **收尾**：改回 `memory` 并重启。

## C 组 · 重试可观测性（模拟瞬时故障）

### C1 能看到"正在重试"，而不是只有最终失败

- **覆盖**：p5.1 + 本次补的重试日志
- **背景**：改动前重试过程**完全没有日志**，生产上"任务怎么慢了几秒"无从排查。
- **操作**：
  1. 临时把所用模型的 `base_url` 改成一个不可达地址（或断开外网），`restart backend`；
  2. 跑一次 A1，观察 backend 日志。
- **预期**：
  1. 依次出现 `LLM 瞬时失败，0.8s 后重试（第 1/2 次）`、`...（第 2/2 次）`；
  2. 最后才是 `LLM brain 调用失败，如实给阶段结论`，前端显示「模型暂不可用」；
  3. **不会**出现无限重试或长时间卡死。
- **对照实验**：设 `LLM_MAX_RETRIES=0` 再跑一次 → 无任何重试日志，直接降级，失败更快。
- **⚠️ 收尾**：务必恢复 `base_url` 与 `LLM_MAX_RETRIES`，否则后续任务都会失败。
