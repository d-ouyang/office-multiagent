**基线**：`cursor/skill-layer-p1` 分支，基于 master（`d21cf0e`，含 p6.39）。初稿 2026-10-24，**2026-10-26 随 P1 落地更新**。

## 一、结论先行

| 问题 | 结论 |
| --- | --- |
| Skill 放哪？ | `backend/app/skills/` 作为一等模块（与 `orchestration` / `core` 并列）。每个 skill 一个目录，含 `spec.yaml`（声明）+ `prompt.md`（指令）+ `run.py`（可选编排逻辑）。 |
| 和现有 `tools_*.py` / `agents.yaml` 什么关系？ | 目标：`tools_*.py` 下沉为**原子工具**；`agents.yaml` 从"列工具白名单"改为"列 skill 清单"；skill 内部再声明自己用哪些工具。**P1 未动这两处**（P3 才做），P1 只新增 skills/ 并复用现有 `tools_*.py` 已注册的原子工具。 |
| 要不要做？ | **建议做，但增量引入**：先不碰运行时，只新增 `skills/` 目录 + 注册表，把已有的业务能力逐步"包"成 skill；跑通后再切 `agents.yaml`。 |
| 对齐参考架构 | 补齐参考架构里缺失的「Agent Skills（能力管理、任务路由）」独立组件，以及 ⑧ 加载 Skill 上下文 步骤。现有 AgentSpec 已是 skill 雏形，只是还寄生在 Agent 上。 |
| 风险红线 | ① skill 与 tool 概念不能混淆（skill 是能力包，tool 是原子函数）；② spec 必须 fail-closed（未知 skill 回落 `general`）；③ 多 skill 并发时状态/上下文必须隔离。 |

一句话：**skill = 角色/指令 + 工具集 + 记忆访问权限的"可复用能力包"，它介于 tool（原子函数）和 agent（运行时实体）之间。把它独立出来，agent 才不会被一长串工具白名单淹没。**

---

## 二、Skill 是什么（与 Tool / Agent 的边界）

| 层级 | 是什么 | 粒度 | 例子 | 落点 |
| --- | --- | --- | --- | --- |
| **Tool** | 原子函数，无业务语义，纯执行 | 最小 | `db_query` / `write_document` / `render_chart` | `orchestration/tools_*.py`（现状）→ P3 下沉为 `orchestration/tools/` 包 |
| **Skill** | 可复用能力包：声明式 spec + 指令 prompt + 一组 tool + 记忆访问权限 | 中 | `doc_writing`（写文档）/ `export_orders`（导出订单）/ `knowledge_qa`（知识库问答） | **P1 已建** `app/skills/` |
| **Agent** | 运行时实体，被指派一组 skill，负责调度执行（single ReAct / multi DAG） | 大 | `general` / `sales_assistant` | `orchestration/agents.py` + `agents.yaml` |

为什么需要这一层：现在 `tools_write.py` / `tools_export.py` / `tools_rag.py` 等"既当工具又当能力"，`agents.yaml` 里 AgentSpec 直接列十几个工具白名单。结果是——加一个业务域就要改 Agent 白名单、能力逻辑散落在 tools 文件里、Agent 之间难以共享同一能力。Skill 层把"业务能力"抽象出来，Agent 只需声明"我会用哪些 skill"。

## 四、SkillSpec 契约（P1 已实现）

### 4.1 `spec.yaml` 字段

| 字段 | 类型 | 说明 | 缺省 |
| --- | --- | --- | --- |
| `name` | string | skill 唯一 ID，被 `agents.yaml` 引用（缺省取目录名） | 目录名 |
| `title` | string | 展示名 | `name` |
| `description` | string | 能力描述（清单/调试用） | 空 |
| `triggers` | list | 触发条件；支持**纯字符串**（当关键词）或 `{intent, keywords}` | 空 |
| `tools` | list | 该 skill 可使用的原子工具白名单（从 `ToolRegistry` 取，未注册则跳过） | 空 |
| `model_preference` | string? | 优先模型；**留空 = 跟随会话/默认模型**，不在 skill 层强制 | 空 |
| `memory` | object? | `session_read` / `user_longterm` / `semantic_search` | 全 false |
| `fallback` | string? | 失败回落的 skill | `general` |
| `enabled` | bool | 开关，**fail-closed 缺省 `false`** | false |

### 4.2 实际示例：`backend/app/skills/doc_writing/spec.yaml`

```yaml
name: doc_writing
title: 文档写作
description: 把已经得到的结论写成 md、docx、pdf 或 pptx 文件

triggers:
  - intent: write_document
  - keywords: ["写文档", "生成报告", "导出 word", "生成文档", "写成 pdf", "演示文稿"]

tools:
  - write_document
  - render_chart
  - clean_table

model_preference: ""   # 空 = 跟随会话/默认模型

memory:
  session_read: true
  user_longterm: false
  semantic_search: false

fallback: general
enabled: true          # P1 参考实现显式打开，便于验证加载链路
```

### 4.3 `run.py` 契约

`run(ctx: SkillContext, **kwargs) -> {"ok": bool, "output"/"error"}`。

- `SkillContext` 只带：受限后的 `tools` + `engine` / `username` / `user_id` / `task_id`。
- **不重新实现原子能力**：`doc_writing/run.py` 只做 format 归一化与白名单校验、title/content 必填校验，然后委托给受限工具集里的 `write_document`。
- 失败返回 `{"ok": False, "error": ...}` **不抛异常**，让上层能如实降级；拿不到工具时返回 `CAPABILITY_MISSING`。

## 六、加载与路由流程（P2 目标）

```
用户请求
  ↓
Planner（意图识别 + 复杂度）          ← 不变
  ↓
Router（skill 级路由）
  ├─ 显式指定 @skill         → 直接加载
  ├─ 意图/关键词匹配 triggers → 加载对应 skill
  └─ 无匹配                → 回落 general（fail-closed）
  ↓
SkillRegistry.load(skill)
  ├─ 读取 spec.yaml（工具白名单 + 记忆权限 + 模型偏好）
  ├─ 读取 prompt.md         → 注入 system prompt
  └─ restrict_tools()       → 仅暴露该 skill 声明的 tools
  ↓
Agent 运行时（single ReAct / multi DAG）执行
```

优先级：**显式 skill 指定 > 意图/关键词匹配 > 默认 general**。多 skill 并行（multi DAG）时，每个子任务独立加载自己的 skill 实例，状态/上下文隔离，避免工具越权。

## 七、可选：对齐外部 Skill 市场

`spec.yaml` 的声明式结构天然兼容外部 skill 描述格式（如 WorkBuddy skill 的 frontmatter）。未来可从市场拉取 skill 包（目录 + spec + 可选 run.py）直接注册进 `SkillRegistry`，**运行时零改动**即可获得新能力。

红线：① 外部 skill 的 `run.py` 必须走代码沙箱/权限隔离，不能直连生产 DB；② 外部 skill 的 `tools` 白名单必须二次校验，防止声明了未授权工具。

**风险与纪律**：
- skill 与 tool 概念严格区分，避免"又在 skill 里写原子逻辑"。
- 所有 spec 默认 `enabled: false`（fail-closed），上线一个开一个。
- 多 skill 并发必须实例隔离，`run.py` 不得持有跨任务的全局可变状态。
- 迁移期 P1–P3 允许"skills 与 tools_*.py 并存"，通过开关灰度，禁止一次性大改写。
