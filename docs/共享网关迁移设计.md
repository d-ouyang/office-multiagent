# 共享 API 网关迁移设计（RAG + office 及未来应用）

> 版本：v1.0.0 · 日期：2026-10-19 · 状态：待评审
> 范围：跨 `rag-qa-system` 与 `office-multiagent` 两仓的网关层架构决策。
> 读者：含后端/运维经验较浅者，故专设「术语速懂」用通俗语言讲清两个关键概念。

---

## 0. TL;DR（一页结论）

- **该收拢**：RAG 和 office 现在是两个几乎一样的 NestJS 网关（都做 JWT 验签、身份头剥离、内部令牌、NDJSON 透传）——重复造轮子，应收拢成**一套共享 API 网关**，未来新应用只注册一条路由即可接入。
- **认证只在一个地方做**（避免双认证），**授权分散在各后端**（网关保证"身份是真的"，后端判"身份够不够"）。
- **划清南北/东西向**：用户→网关→业务走用户 JWT（南北向，网关管）；服务↔服务走内部令牌/mTLS（东西向，不过用户网关）。
- **认证放哪**：近期用「单一共享网关验 JWT、后端信任注入身份」（方案 B；若公司已有可信总网关则用方案 C）；**中期上独立 IdP（非对称签发/验签分离）**（方案 D）。
- **两个必须配套的工程点**：网关要**无状态**、跑**多副本**，否则共享网关会从"提效"变成"全线单点"。

## 1. 背景与问题

现状（两仓各持一个网关）：

| 服务 | 链路 | 网关形态 |
|---|---|---|
| RAG 问答 | 浏览器 → NestJS(:3000) → FastAPI(:8000) | `rag-qa-gateway`：passport-jwt 验签 + 剥离 8 个身份头 + `X-Internal-Token` + NDJSON 透传 |
| office 助手 | 浏览器 → NestJS(:3001) → FastAPI(内网) | `office-gateway`：同上，一套同源逻辑 |
| 未来新应用 | ? | 若照现状，得再抄一遍网关 |

问题：
1. **重复**：认证、信任边界、流式透传逻辑两套（将来 N 套），改一处要改多处、易写漏。
2. **口径不一**：两个网关的安全策略（哪些头该剥、哪些路径公开、限流阈值）各写各的，容易出现"一个严一个松"。
3. **接入成本高**：新应用要重新实现一整套网关才能达到同等安全/流式能力。

目标：**一套网关，多个上游**；认证单点、信任边界单点、横切关注点单点；新应用零成本接入。

## 2. 术语速懂（通俗版）

> 这一节写给"非安全/后端专项"的同学。用一个银行的比喻把几个概念串起来。

### 2.1 API 网关是什么
银行的**统一进门大厅**：所有人先进大厅，大厅核验你的身份、看你去哪个窗口、登记放行；你不需要自己闯到金库。对应到系统：所有请求先到网关，网关验身份、按地址转给对应后端、记录日志。后端只信任"从大厅正规进来的人"。

### 2.2 认证 vs 授权（authN vs authZ）
- **认证（authN）**："你是谁？票是真的吗、过期没？" —— 网关干这个。
- **授权（authZ）**："你这个身份，够不够资格进这个房间？" —— 各后端用自己的角色模型干（RAG 的 `kb_role`、office 的 roles）。
- 一句话：**网关验真伪，后端判权限**。别让网关越权去判业务权限（它不懂业务），也别让后端去信客户端自称的身份（会被伪造）。

### 2.3 JWT 是什么
一张**防伪的电子票据**，分三段（头.载荷.签名）：头说"用什么算法"，载荷装身份信息（用户 id、角色、过期时间），签名是"防伪章"。验签 = 检查这章是真的且没被改、没过期。我们现在的签名算法是 **HS256（对称）**：签章和验章用**同一把秘密钥匙**（`JWT_SECRET`）。

### 2.4 独立 IdP + 签发/验签分离（重点，通俗讲）

**这是什么技术**：IdP = Identity Provider，身份提供方，一个**专门负责"登录 + 签发票据"的独立服务**（比如 Keycloak、Authing、或自建的 OAuth2/OIDC 服务）。"签发/验签分离"指把"盖章"和"验章"的能力用**两把不同的钥匙**分开——技术上叫**非对称加密**（公钥 / 私钥）。

**原理（比喻）**：
- IdP 手握一把**私钥**（只有它有的"印章"），只用它来**签发** JWT。
- 网关和各后端只拿到**公钥**（公开的"验章指南"），只能用公钥来**验签**——能验证"这票确实是 IdP 签的、没被改、没过期"，但**仿造不出**新票。
- 公钥可以随便公开分发（泄露了也无所谓，反正仿不了章）；私钥锁在 IdP 一处。

**对比现在的 HS256（对称，一把钥匙）**：

| | 现在：对称密钥（HS256） | 目标：独立 IdP（RS256/ES256 非对称） |
|---|---|---|
| 钥匙 | 签和验**同一把** `JWT_SECRET` | IdP 持私钥签发；网关/后端持公钥验签 |
| 谁能签发票 | 任何拿到这把钥匙的人（登录服务、网关、后端都可能拿到） | **只有 IdP** |
| 泄露后果 | 一处泄露 = 全员能被伪造身份 | 公钥泄露无妨；只有 IdP 私钥泄露才出大事，且暴露面仅一处 |
| 轮换 | 签+验同时换，所有方要同步，易踩窗口期 | 公钥可随时轮换（不影响安全）；私钥仅在 IdP 轮换 |
| 额外收益 | — | 为 SSO 单点登录、多端、第三方登录、更细的 scope 打基础 |

**一句话**：现在是"一把钥匙开所有门还谁都能配钥匙"；上 IdP 后是"只有一个配钥处（IdP），其他门只配'验章器'（公钥），配钥处锁死、验章器随便发"。

**落地形态**：JWT 签名算法从 HS256 换成 RS256/ES256；IdP 暴露一个 **JWKS 端点**（公钥集合，公钥放这、支持热轮换），网关和后端从这个端点拉公钥来验签。

### 2.5 无状态 + 多副本（重点，通俗讲）

**无状态（stateless）**：网关**自己不记**"你是谁、你上次干了什么"。每个请求自带全部所需信息（JWT 里就带身份），网关验完就转发，不在自己内存/磁盘存会话。
- 比喻：火车站**验票闸机**——每张票自带身份，闸机只验真伪，不记"这人来过"。所以多开几个闸机，乘客到任意一个都能过。
- 反面（有状态）：若把登录会话存进"网关 A"的内存，乘客下次被分到"网关 B"就"掉登录"。要么粘连（固定把人分到同一台，牺牲扩展还留单点），要么外加共享会话存储（Redis）——都是自找麻烦。
- 我们的 JWT 验签天生无状态（不查库、不存会话），所以网关**天然适合无状态化**。

**多副本（replicas）**：同时跑**多个完全相同的网关实例**（多个容器），前面加一个**负载均衡器**（nginx/Caddy/云 SLB）把流量分流到不同实例。
- 比喻：银行开**多个相同窗口**，大堂经理（负载均衡）把客户分流。
- 好处：① **高可用**——一个实例挂了，其他顶着，服务不断；② **水平扩容**——流量大涨就加窗口，加一个是一个。
- **前提是"无状态"**：因为状态不依赖某个实例，请求分到哪个实例结果都一样。有状态的话多副本会对不上（会话丢），所以**无状态是多副本能成立的前提**，两者必须配套。

**落地**：compose 里 `deploy.replicas: N`（或 K8s `replicas`），前面挂负载均衡。共享网关一旦收拢，就**必须**这么配，否则它从"提效"变成"全线单点"。

### 2.6 南北向 vs 东西向
- **南北向**：用户/浏览器 → 网关 → 业务（外部流量），走**用户 JWT**，网关统一认证。
- **东西向**：服务 ↔ 服务（如 office 调 RAG 检索），走**内部令牌 / mTLS**，**不过用户网关**。把东西向塞进用户网关会把"用户态"和"服务态"耦合，很危险。

### 2.7 信任边界（trust boundary）
"哪些身份信息可以信"的那条线。规则：**客户端传来的身份头一律不可信，网关剥掉，再用验过的 JWT claims 重注入可信身份头**；后端只信网关注入的头，绝不信客户端自报的。这样客户端伪造就废了。

### 2.8 用户身份架构（2026-10-20 讨论结论）

**先分三层，别混**：

| 层次 | 是什么 | 结论 |
|---|---|---|
| L1 认证机制 | 一个网关验一种 JWT、一个信任边界 | ✅ 网关统一（本设计已达成） |
| L2 身份归一 | 同一个人在所有系统里是同一个人 | **employee_id（工号）为全局身份键** |
| L3 账号数据 | 一张用户表 / SSO | **各域分离、不合并**；触发条件满足再上 IdP |

**身份键三层（重要裁决）**：

| 概念 | 定位 | 唯一性 |
|---|---|---|
| `employee_id` 工号 | "人"的唯一标识，**永不复用**（HR 纪律） | 全局唯一 → JWT `sub` + 跨系统注入键 |
| `username` 登录名 | 登录凭据，可改（改名/换拼音） | 仅单个账号目录内唯一；**不作身份键**（重名必然撞：zhang.wei×N） |
| `display_name` 姓名 | 仅展示 | 可重复 |

**配套裁决**：
- JWT `sub = employee_id`；网关注入 `X-Employee-Id`（身份解析键）+ `X-Username`（降级为展示/日志，不作解析键）。修正 p5.0b 的临时方案（当时两边 user 表无工号列，借道 username）。
- **两套用户库不合并**（RAG 存 kb_role、office 存 model_pool_id/额度）——域字段不同，合并=可空列泥潭+迁移/审计/备份互相牵连；网关只传身份，不理解域数据，保持"薄"。
- office 的 `user.kb_role` 列是 init.sql 早期借 RAG 命名的历史遗留（office 权限维度=model_pool_id），p6.1 登录前删除。
- RAG `user` 表加 `employee_id`（UNIQUE，alembic），`resolve_actor` 优先按工号解析；过渡期（加列前）跨系统仍注 `X-Username`。
- IdP 触发条件不变（第三应用/SSO/密码策略集中）。届时 IdP 只管"人"（账号/密码/登录），域授权表继续分居，`employee_id` 即关联键——机制无缝升级。

## 3. 目标拓扑与职责边界

拓扑（见下方示意，亦可对照此前的拓扑图）：

```
客户端(带 JWT)
   │  南北向
   ▼
┌────────────────────────── 共享 API 网关（无状态 · 多副本 · 负载均衡在前）──────────────────────────┐
│  验 JWT → 剥离客户端身份头 → 重注入可信身份 → 按 host/path 路由 → 注入内部令牌 → 限流/CORS/日志 → NDJSON 透传  │
└───────────────────────────────────────────────────────────────────────────────────────────────────────┘
   │                    │                        │
   ▼                    ▼                        ▼
RAG 后端(内网)     office 后端(内网)       未来新应用(内网)
各自做授权(kb_role / roles)                   零成本接入
（东西向：服务↔服务走内部令牌/mTLS，不过此网关）
```

**网关做（authN + 横切）**：验 JWT 有效期/claims；剥离+重注入身份头；host/path 路由；注入内部服务令牌；限流/CORS/correlation-id/访问日志；NDJSON 不缓冲透传。

**网关不做**：不碰业务逻辑；**不做授权**（authZ 留后端，fail-closed）；不存用户会话（保持无状态）。

## 4. 认证放哪：决策矩阵（核心）

| 方案 | 认证在哪 | 安全强度 | 重复实现 | 单点风险 | 新应用接入成本 | 流式(NDJSON)支持 | 改造量 | 适合阶段 |
|---|---|---|---|---|---|---|---|---|
| **A 现状**：各服务各持网关，各验各的 JWT（HS256 对称） | 每个服务网关 | 中（一把对称密钥全员能签） | **高**（两套→N 套） | 双点各崩各的 | 高（再抄一套） | 各自实现 | — | 现状，**淘汰** |
| **B 单一共享网关**：一层网关验 JWT，后端信任注入身份 | 共享网关一处 | 中高（认证单点管控） | 低（一套） | 有（须配多副本） | 低（注册一条路由） | 网关统一保证 | 中 | **近期推荐** |
| **C 公司总网关 + 薄代理**：公司已有可信总网关验 JWT，service 侧只留薄流式代理（信任注入身份） | 公司总网关 | 高（复用公司基建） | 低 | 公司级（已存在） | 低 | 薄代理专保流式 | 小 | 若**已有可信总网关** |
| **D 独立 IdP（非对称）+ 网关验签**：IdP 私钥签发，网关/后端公钥验签 | IdP 签发 + 网关/后端验签 | **高**（私钥集中、泄露面小） | 低 | IdP 单点（可集群） | 低 | 不变 | 大 | **中期目标** |

**怎么选（决策 guidance）**：
1. **先问：公司是否已有一个"验 token 的总网关"且可信？**
   - **有** → 走 **C**：认证放总网关，office/rag 的 NestJS 网关**退化为薄流式代理**（只保留 NDJSON 透传和路由，**别再验一次用户 JWT**，改为信任总网关注入的身份）。改造最小、不双认证。
   - **没有** → 走 **B**：把 office 网关演进成共享网关，认证放它，后端信任它注入的身份。
2. **无论 B 还是 C，都要消除"双认证"**（总网关验一次、service 网关又验一次 = 浪费且两处密钥要同步，还容易出现"一个过一个不过"的怪问题）。
3. **中期演进到 D**：等流量/应用数上来、或要多端/SSO 时，上独立 IdP，把"签发"从应用里彻底拿走，网关和后端只验签。
4. **A（现状）是要淘汰的中间态**，不要在新应用上复制。

**贯穿原则**：认证单点；授权分散后端；信任边界单点；东西向与南北向分离。

## 5. 落地方案（分期，跨两仓）

**Phase A · 共享网关骨架（近期，office 仓内，先自接入）**
- 把 `office-gateway` 重构成**配置驱动路由表**：`host/path 前缀 → 上游 URL + 该剥哪些头/注入哪些头 + 是否公开`。
- 先只注册 office 自己一个上游，**行为与现有测试不回归**（用现有 `proxy.e2e.spec.ts` 系列守）。
- 网关保持无状态（确认不引入内存会话）、补 `deploy.replicas` 配置样例 + 前置负载均衡说明。

**Phase B · 接入 RAG + 定认证点（核心迁移）**
- 决定认证放 B 还是 C（见 §4 决策 guidance）。
- RAG 后端注册为上游；把 RAG 的"8 头剥离 / NDJSON / `X-Internal-Token`"策略搬进路由表。
- **消除双认证**；RAG/office 后端统一改为"信任网关注入身份"，各自后端继续做授权。
- 灰度：先让 RAG 或 office 之一切到共享网关，另一个观察，再全切。

**Phase C · 横切加固 + 高可用**
- 限流、统一错误体、correlation-id 全链路、访问日志。
- 网关**多副本 + 负载均衡**（无状态已保证可横扩）。
- 中期：上**独立 IdP**（JWKS + RS256），完成签发/验签分离。

## 6. 风险与注意（⚠️ 特别标明，详细解释）

> 这一节是重点。收拢网关是"提效"与"制造单点"并存的操作，下面每条都要在落地前想清楚。

**⚠️ R1 单点故障（SPOF）——收拢的最大代价**
- **是什么**：所有应用共用一个网关，它挂了 = 全线 502。
- **为什么危险**：现状是"各崩各的"（RAG 挂不影响 office），收拢后变成"一损俱损"。
- **对策**：**必须无状态 + 多副本 + 负载均衡 + 健康检查**（§2.5）。这是收拢的**前置条件**，不是可选项。配不上多副本就不要收拢。

**⚠️ R2 双认证（迁移期最容易踩）**
- **是什么**：公司总网关验一次 JWT，service 网关又验一次。
- **后果**：浪费；两处密钥/策略要同步；更麻烦的是"总网关放过但 service 网关拒了"这类精神分裂问题，极难排查。
- **对策**：明确"认证只在最后一跳之前的那一个点做"，其余层级只做路由/透传，**不碰用户 JWT**。

**⚠️ R3 共享密钥管理与轮换**
- **是什么**：HS256 对称方案下，签和验同一把 `JWT_SECRET`，网关、登录服务、可能的后端都拿它。
- **后果**：泄露面大；轮换要所有方同时换，有窗口期（旧 token 突然全失效 → 大规模掉登录）。
- **对策**：短期严控密钥分发范围 + 计划内轮换；**中期上独立 IdP**（§2.4）用非对称把"签"和"验"分开，私钥集中、公钥可随便轮换。

**⚠️ R4 爆炸半径（blast radius）**
- **是什么**：网关一处配置/代码改动，影响所有应用。
- **对策**：配置变更走灰度 + 可回滚；路由表按应用分文件/分块，改一个不影响其他；有自动化测试守每一条路由的透传与鉴权行为。

**⚠️ R5 流式被缓冲（NDJSON/SSE 的坑）**
- **是什么**：通用网关/反代默认可能缓冲响应，导致流式卡成"一次性返回"，前端逐字效果全无。
- **对策**：网关透传必须 `selfHandleResponse:false` + `Accept-Encoding:identity`；反代 `proxy_buffering off` + 放长 `read_timeout`（office/rag 网关已是这个纪律，迁移时别丢）。

**⚠️ R6 东西向流量误入用户网关**
- **是什么**：把服务间调用也走过用户网关。
- **后果**：用户态与服务态耦合；内部调用被套上用户 JWT 语义，权限模型混乱。
- **对策**：东西向走**内部令牌 / mTLS**，与南北向物理/逻辑分离（§2.6）。

**⚠️ R7 授权后置到后端，别在网关做**
- **是什么**：试图让网关判"这个角色能不能调这个接口"。
- **后果**：网关被迫懂每个应用的业务权限，改一处动全身，且极易和 backend 的真实权限模型不一致。
- **对策**：网关只认证 + 传可信身份；**授权在各后端 fail-closed 自判**。

**⚠️ R8 身份头伪造（信任边界被绕）**
- **是什么**：客户端自己带 `X-User-Id` 之类的头，后端却信了。
- **对策**：网关**剥离所有客户端身份头**，仅用验过的 JWT claims **重注入**；后端只认网关口注入的头（`IDENTITY_MODE=gateway` 那套信任边界纪律，两仓都已建立，迁移时必须保留）。

**⚠️ R9 可观测性缺失**
- **是什么**：共用一个入口后，出问题难定位是哪个上游、哪一跳。
- **对策**：网关注入 `correlation-id` 并全链路透传；按上游分别打访问日志/指标；错误体带 `requestId`。

**⚠️ R10 过渡期两套并存的口径漂移**
- **是什么**：迁移期间新旧网关并存，安全策略慢慢对不上。
- **对策**：把安全策略（公开路径、剥哪些头、限流）抽成**一份共享配置**，新旧网关都读它；迁移完成后下线旧网关。

## 7. 迁移检查清单与回滚

**上线前检查清单**：
- [ ] 网关无状态（无内存会话，重启/漂移不掉登录）
- [ ] 多副本 + 负载均衡 + 健康检查就位
- [ ] 每一条上游路由都有透传 + 鉴权自动化测试守（含公开路径、401、有效 JWT、NDJSON 透传）
- [ ] NDJSON 透传无缓冲验证过
- [ ] 身份头剥离/重注入有"反向验证"（拆掉护栏后测试必须转红）
- [ ] 东西向未误入用户网关
- [ ] correlation-id 全链路通
- [ ] 灰度开关 + 回滚脚本就位

**回滚**：路由表切回旧上游/旧网关（域名或路径前缀级回切），因为网关无状态，回滚不丢会话。
