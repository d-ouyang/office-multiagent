# PLAN-2.4.2 · 上下文正确性 · 预算 · 对账 · 可观测

> 2026-11-18 · 承接 v2.4.1（引导入口与结果完整性）
> 状态：**待你拍板**。本文只列"要改什么、为什么改、风险多大"，不含实现。

## 0. 一句话

v2.4.1 之后暴露出来的问题，全部集中在三类：**上下文拼得不对（记忆）**、**预算分配不准（成本/质量）**、**账和过程看不见（对账/回放）**。没有一条是业务功能缺失。

## 0.1 已拍板的决定（2026-11-18）

| 决定 | 结论 |
| ---- | ---- |
| 结构化摘要是否调用小模型 | **接受**（每轮一次，200~500 token） |
| P4 covers 收窄 / agent 精简 | **本版不做**，等 P0-P2 稳定后单独评估 |
| 完整回放（对比视图/schema/产物内嵌） | 放 **2.4.3**；2.4.2 只做时间轴最小版 |

## 2. 分批方案

### P0 · 上下文正确性（bug 级，必做）

**A1+A3+A6：近 8 轮原文，丢整轮不切句，最近 2 轮硬保留**

- 改：`history_recent_rounds` 4 → 8；`compress_rounds` 不再用于近期轮次，近期轮次**原文直出**
- 超预算时：**整轮丢弃**（移入摘要），绝不切半句
- **硬底线：最近 2 轮 + 本轮问题永远完整保留**，任何降级都不得动它们
- 为什么：现在的 80 字让"多轮对话"事实不成立（第二轮就丢关键信息）。4 轮 × 1000 字只占 1M 窗口的 0.4%，没有省的必要
- 风险：长会话（50 轮）时 token 上升 → 靠 A2 的摘要 + 下面的降级链兜住

**预算降级链（必须按顺序，前一步不够才走下一步）**

```
1. 最老的整轮对话 → 生成结构化摘要进 L3（第 9 轮起，逐轮推进）
2. 摘要总量超预算 → 把最老的几条摘要合并成一条（合并已有结果，不重读原文）
3. 还不够 → 继续丢更近的轮次（8 → 6 → 4 轮）
4. 硬底线：最近 2 轮 + 本轮问题 + 系统提示，永不裁剪
```

验收：人为把窗口压到很小，任务仍不报错，且最近 2 轮完整（对应"塞满窗口不报错"）。

**A2+A5：结构化摘要（一轮一条，永久复用）**

- 新表 `session_summary(session_id, turn_no, payload json, rendered text)`
- `payload`：`{user_intent, keys(指标/筛选/分组), conclusions[], artifacts[], open_questions[]}`
- 每轮结束生成一条并落库；**已生成的永不重算**；只有在摘要总量超预算时，才把最老的几条**合并**
- 为什么：切片的"历史摘要"没有语义；且没有 turn_no 无法绑定
- 风险：多一次小模型调用（每轮 200~500 token，可忽略）；生成失败回落原文切片（不阻断）

**A4：open_questions 驱动指代对齐**

- 每轮把"助手最后问的问题 / 待确认项"存进 `open_questions`
- 下一轮若存在 open_questions，注入：
  `用户这轮的「需要/继续/你看着办」是在回应：『需要我导出成文档吗』`
- **不依赖词表**（词表不可穷尽），只要有悬着的提问就注入
- 为什么：「需要」事故的直接原因之一
- 风险：低。最坏情况是多注入一段几十字的说明

**验收**
- 会话里问「需要」「继续」「按你推荐的来」三种说法，都能正确续做
- 连问 3 轮不丢上文
- 20 轮后，摘要里仍能查到第 1 轮的结论

### P1 · 预算与输出（成本/质量）

**B1：输出预留分档**

- 决策步 1024，终答步 8192（`reserve_call` 已支持传参，改 brain 调用处）
- 为什么：一个只写 300 字的步骤占 8192，预算紧时会提前判"达上限"

**B2：历史预算 60% → 75%**

- 配置项 `history_budget_window_pct`（运行时可调，无需发版）
- 为什么：现在 76,800 偏保守，配合 A1 的原文直出会更容易触顶
- 风险：给输出留的空间从 40% 降到 25%，极端长答可能被挤 → 观察即可，可随时调回

**B3：观察截断补续读指引**

- 截断时追加一句"可用 offset 续读；或用 headings 定位章节"
- 为什么：模型现在知道被截断，但不知道能续读

**B4：表格预览 50 行 + 列统计**

- 预览 20 → 50；额外给每列 `min/max/均值/空值数/唯一值数`
- 为什么：让模型"看 500 行"是浪费 token 且注意力稀释；列统计比多看 30 行有用得多
- 风险：低（token 增加约 300）

### P2 · 对账（财务正确性）

**C1：账本加 actual 列 + 对账视图**

- `token_ledger` 增 `actual`；管理端加"任务对账"页：`reserve / actual / billed / 差额`
- 为什么：现在 settlement 记的是折扣后额度，真实用量在别处，**对不上账**——缓存折扣（0.25）会让人看到"用 1000 扣 400"却无法核对
- 风险：迁移加列（可空，不影响旧数据）

### P3 · 可观测与回放（你最关心的"能回放吗"）

**D1+D2：`llm_call` 表**

- 每次模型调用落一行：`run_id / step / agent / model / messages_json（脱敏）/ response_text / prompt_tokens / completion_tokens / ms`
- 为什么：现在模型收到什么、返回什么，都不落库，出问题只能靠日志猜

**D3：工具调用补参数与结果**

- `tool_invocation` 增 `params / result_summary`（完整结果太大，存摘要 + 引用）
- 为什么：现在只有 `args_hash`，看不到"传了什么、返回了什么"

**回放接口 + 界面（2.4.2 只做最小版）**

- `GET /api/v1/runs/{id}/context`：返回每步的 messages（脱敏）
- 管理端任务详情**时间轴最小版**：按步骤列出「序号 / Agent / 工具名 / 耗时 / 成败」，
  点开能看到「模型这次收到什么（拼装后的文本）、输出什么、工具参数与结果摘要」
- **以下放 2.4.3（完整回放）**：多轮对比视图、工具 schema 展示、产物内嵌预览、
  按 token 高亮的上下文占用视图
- 为什么：现在"回放"只有事件名，看不到内容；但完整回放工作量大，且不影响正确性

**D4：事件补发（可选）**

- `GET /runs/{run_id}/events?after_seq=N`，从 `message.trace` 读
- 为什么：断连后只丢打字机效果，结果已落库；优先级低
- **不做**服务端内存缓冲（多实例失效、可靠性差）

### P4 · Agent 整理（**本版不做**，2026-11-18 拍板：先观察）

> 原因：covers 收窄会改变路由行为，可能让更多任务走 multi（成本上升）。
> 等 P0-P2 稳定后再单独评估。

**F1：`image_restore` 空壳**

- 二选一：接 OCR（独立工作量）或从 planner 意图表移除（5 分钟）
- 建议：**先移除**，避免引导用户点到"暂不支持"

**F2+F3：covers 收窄**

- 现在 `analysis` 覆盖 5 个意图、`report` 覆盖 6 个 → 几乎总是 single，并行触发不了
- 改：把 `rag`、`cleaning` 从 analysis/report 的 covers 里移出，让"制度 + 分析"能真并行
- 风险：**会改变路由行为**，可能导致更多 multi（成本上升）。建议先在小流量观察，或做成运行时开关

## 3. 明确不做的

| 项 | 原因 |
| -- | ---- |
| 事件级断点续推（内存缓冲） | 多实例失效；结果已落库，收益低 |
| RAG 召回历史对话 | 办公场景连贯性优先，检索不确定性高 |
| `image_restore` 接 OCR | 独立工程，不在本版 |
| 把工具全过程原文回灌上下文 | 每轮重读几万字，成本与注意力双输；改存"纪要" |

## 4. 风险与回滚

| 改动 | 风险 | 回滚方式 |
| ---- | ---- | -------- |
| 近 8 轮原文 | 长会话 token 上升 | `history_recent_rounds` 运行时可调回 4 |
| 历史预算 75% | 长答被挤 | `history_budget_window_pct` 调回 60 |
| 结构化摘要 | 多一次小模型调用；生成失败 | 失败回落切片；开关 `context_engine=legacy` |
| covers 收窄 | 更多 multi，成本上升 | 配置改回，无需发版 |
| ledger 加列 | 迁移 | 列可空，旧数据不受影响 |

## 5. 验收标准

| 场景 | 期望 |
| ---- | ---- |
| 「需要」/「继续」/「你看着办」 | 三种都能续做上一轮的事 |
| 连问 3 轮 | 第 1 轮的关键结论仍在上下文里 |
| 20 轮长会话 | 摘要含第 1 轮结论；token 不随轮次线性涨 |
| 9.3 万字文档 | 仍走目录索引，不因预算调整而退化 |
| 任务详情 | 每一步能看到"模型收到什么、返回什么、工具做了什么" |
| 对账页 | 每条任务 reserve/actual/billed 三项齐全，差额可解释 |

## 6. 工作量

| 批次 | 内容 | 规模 |
| ---- | ---- | ---- |
| P0 | 原文直出 + 摘要表 + open_questions + 丢整轮 | 1 天 |
| P1 | 分档 + 预算比例 + 续读指引 + 表格统计 | 半天 |
| P2 | ledger 列 + 对账视图 | 半天 |
| P3 | llm_call + 工具参数 + 回放接口 + 时间轴 | 1.5 天 |

**建议先做 P0 + P2**：前者是正确性 bug，后者是财务正确性，两者风险最低、收益最直接。
P3 工作量最大但最不紧急（它解决"看不清"，不解决"不对"）。
