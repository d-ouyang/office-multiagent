# v2.3.0-p1.1 · 上下文预算化（C 层补全第二步）

> 2026-11-16 · 分支 `feature/2.3.0-context-budget` · pytest 571 → **581 passed / 3 skipped**
> ⚠️ **未部署**（本地已提交，未打 tag）

## 为什么

p6.9 把四条截断链路放大到 24000 字之后，历史占用变成"每步 24K × 步数"，没有总量约束：

- 4~5 步 × 24000 汉字 ≈ 24K token/步 ≈ 96K，加上系统提示、13 个工具说明、协议模板、
  历史摘要，128K 窗口触手可及；
- `core/llm.py` 对 `context_length_exceeded` **没有任何专门处理**（`_is_transient` 只认
  429/5xx/网络错），400 直接上抛 → 任务收尾失败；
- 跑不跑得通取决于用户文档多大、模型走了几步，而不是设计保证。

p1.0 让"每步不炸"，p1.1 让"总量可控"。

## 算法（五条规则）

`orchestration/context_budget.py::budget_steps(steps, max_tokens, step_cap)`：

1. **最近优先**：从最后一步往回装，原文装不下才转降级；
2. **整块降级**：旧步变"调用了 X，N 个参数，返回 M 行：要点…"，绝不切半句；
3. **末步保底**：最后一步即使自身超预算也保留，但**最多吃 60% 预算**；
4. **seed 免疫**：无工具调用的步（HITL 用户补充输入）不可再生，永远保留；
5. **0 = 不限**：回退到 p1.0 的逐条截断，行为逐字一致（B-4 锁定）。

为什么是"降级"而不是 rag 那种"整块丢弃"：观察里的数字是终答的依据，丢掉会让模型
要么编、要么反复重查；压成要点至少保住"查到了什么、有多少"。

## 改动

- 新建 `orchestration/context_budget.py`（放这里而非 `core/`：依赖 `memory.estimate_tokens`，
  放 core 会造成 core→orchestration 反向依赖）。
- `brain._render_history` / `_messages_for_tool_calls` 双协议共用 `BudgetResult.obs_text`——
  同一份判定，换协议不换行为。
- `graph._history_budget()`：**模型窗口 × 百分比**（新开关 `history_budget_window_pct`，
  缺省 60，0=不限）。为什么按窗口而不是任务余额：这是单次请求的长度约束，任务累计
  预算由 `TaskTokenBudget` 单独管；混用会让长任务后半程"越跑越瞎"。
- 注入点四处：single、multi 子任务、强制收尾脑（bare）、multi 汇总官——**汇总官最容易超**
  （塞的是各子任务终答）。
- `core/events.py::context_usage` 增 `budget/dropped/notes` 三个纯增量字段。
- `core/token_budget.py::prompt_upper_bound`：UTF-8 字节 → `estimate_tokens` 口径。
  原来中文 1 字算 3 字节，2 万字文档报 6 万"token"，而缺省任务上限 5 万 → 直接误判超限
  暂停（`paused_budget`）。这是 p1.0 暴露出的真实冲突。

## 实现偏差（都在代码里留了注释）

1. **末步保底最初给足全部预算**：实测 2 万字单步会把预算吃光，前面 5 步全被整块省略——
   "最近优先"退化成"最近独吞"。改为最多 60%。
2. **seed 步原本也参与降级**：HITL 续跑的用户回答被压成"调用了（无动作）…"，
   模型等于没收到答案。改为免疫，只截正文。
3. **顺手修 p1.0 遗留**：tool_calls 路径此前静默截断（无"…（已截断）"标注），
   JSON 协议有——同一任务换协议结果不同。统一后两条都标注。
4. **B-9 的断言改了**：原计划写"新上界 ≥ 旧上界 ×0.4"，但中文口径下新值就是旧值的
   1/3，该护栏自相矛盾。改成行为断言："2 万字文档不再被算成 6 万"。
