## 设计决策（不确定时的拍板，依据路线文档 §4.1）

1. **契约位置 `core/` 而非计划文档写的 `orchestration/`**：契约是基础设施层，被 orchestration 消费；放 core 避免层级倒挂（与 llm/model_registry 同层）。
2. **不做阉割版 `invoke(messages, tools, budget)`**：路线文档的最小字段是理想形；本项目已有双协议（json/tool_calls）+ 流式回调 + reasoning_effort + token 预算预约（`token_budget.reserve_call`），强套 invoke 会砍能力。契约面 = 现有能力面，`budget` 暂以 max_tokens 占位，Phase B 升级为结构化预算收口。
3. **门面模式而非改调用点**：llm.chat/chat_stream 保留原签名做转发，brain/react/graph 的 import 零改动——这正是「可替换性」判据本身；将来 LiteLLM adapter（Phase B1）只需注册新实现。
4. **Fake 的 chat_stream 委托 chat**：Fake 用于业务层决策模拟，流式分块语义由真实现与 test_llm 的 MockTransport 用例负责，不重复模拟。
5. **生产不暴露 set_adapter 路径**：注入仅测试用；运行时切换（settings.model_adapter）Phase B 落地，避免半吊子配置面。

## 踩坑（记录给后续步骤）

- **ReAct JSON 协议的消息形态**：brain 把历史拼进**单条 user 消息**（messages 恒为 [system, user]），不存在 assistant 轮次消息——Fake 的按轮分支判断要用 user content 内容（如出现上一轮 action 名），不能用 `role==assistant`（tool_calls 协议才有 assistant/tool 轮次，brain.py L359 注释即此红线）。
- 全局 adapter 注入必须配 autouse fixture 收尾 reset，否则跨用例泄漏假模型（test_model_adapter.py 顶部 fixture）。
