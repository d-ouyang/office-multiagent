# 迭代总结 · v1.0.0-p3.2 — DAG 子任务拆分（Phase 3 收口）

> 对应计划：PLAN-1.0.0.md Phase 3 / v1.0.0-p3.2。Tag：`v1.0.0-p3.2`。至此 **Phase 3 全部完成**。

## 1. 目标
落地设计文档 §四.2 第三步：复杂任务**拆成子任务 DAG + 依赖关系**，接入 LangGraph 编排（multi 节点按拓扑序推子任务状态），`/plan` 对复杂任务附带 DAG。

## 2. 做了什么
- `config/planner.yaml` 新增 `dag.dependencies`：意图依赖表（cleaning→analysis→report/visualization；rag/image_restore 独立可并行）。**配置驱动**。
- `core/decomposer.py`：`decompose(plan) -> DAG`；`Subtask{id, agent_type, intent, depends_on, status}`；`DAG.topo_order()`（Kahn 拓扑排序，**有环 fail-fast 抛错**）；`to_dict()`。被依赖意图不在场则自动忽略该边。
- `orchestration/graph.py`：planner 节点在 multi 时算 DAG 存入 state；multi 节点按 `dag.subtasks` 逐个推 `status(running→done)` + `task_summary`。
- `POST /api/v1/plan`：复杂任务响应附带 `dag`（subtasks + topo_order）。
- 版本 bump `1.0.0-p3.2`。

## 3. 否掉的方案（最值钱）
- **DAG 拆分同样用确定性规则打底，不上调 LLM**：按「检测到的意图 + 配置的意图依赖」生成子任务图，可测、零成本；LLM 分解长尾/歧义留作 `DecisionModel` 插槽（承接 p3.1 与"去掉 JEV"拍板）。
- **依赖只对同时出现的意图生效**：`analysis` 依赖 `cleaning`，但任务里没有 cleaning 时就忽略该边——否则会给单意图任务硬塞不存在的依赖。
- **环校验 fail-fast**：配置写错（A 依赖 B、B 依赖 A）在 `decompose`/`topo_order` 立刻抛错，不留到运行时才炸。
- **p3.2 只拆不定调度**：真实按拓扑序调度 + 并行在 Phase 4 Orchestrator；本轮 multi 节点串行推桩状态证明 DAG 结构正确。
