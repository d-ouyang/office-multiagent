# 迭代总结 · v1.0.0-p5.0b — rag 上游按上游身份注入 + 剥客户端身份头

> 承接 p5.0a（共享网关骨架）与 rag 仓 p4.11（后端认办公网关凭证）。Tag：`v1.0.0-p5.0b`。

## 1. 目标
补齐共享网关 Phase B 的最后一环：转发到 rag 上游时，**剥离客户端伪造的身份头**（信任边界①）、
**注入网关验过的可信身份 + 网关证明**（信任边界②），让 RAG 后端（gateway 模式）凭 `X-Internal-Auth`
认下这次请求。

## 2. 做了什么
- `route-table.ts`：upstream 增 `stripIdentity` / `injectIdentity` / `internalSecret`（`${ENV}` 展开）；
  office 上游不声明 → 行为不变。
- `config/routes.yaml`：rag 上游声明三项；`internal_secret: ${RAG_INTERNAL_SECRET}` 须与 RAG 后端
  `OFFICE_GATEWAY_SHARED_SECRET` 同值（rag p4.11）。
- `proxy.controller.ts`：`proxyReq` 里按上游策略——剥 `INBOUND_IDENTITY_HEADERS`（与 RAG
  `IDENTITY_HEADERS` 一一对应的 9 个头）；注入 `X-Username`(encodeURIComponent) + `X-Internal-Auth`。
- env/compose：加 `RAG_INTERNAL_SECRET`（gateway/.env.example、根 .env.example、compose gateway）。

## 3. 否掉的方案（最值钱）
- **刻意不注入 `X-User-Id`**：两套系统 `user.id` 是两个命名空间，注入数字 id 可能在上游库里
  撞到另一个人的行（静默错身份）；只注 `X-Username`，由 RAG 按 username 回落解析
  （对齐 = 两边用户名一致），查不到就 401 —— fail-closed 方向。
- **不全局剥身份头**：按上游声明（`strip_identity`）生效，office 老路行为零变化；全局化等
  office 后端也走"信任注入"模型时再开。
- **身份注入不做在 guard**（守卫只管验签放行）：做在 proxyReq，离转发最近、每上游策略可控。

## 4. 验证
- `tsc --noEmit` 通过；`nest build` 成功。
- `jest` **28 passed / 4 suites**（+2：路由表身份策略字段映射；e2e 增强断言）。
- e2e 实证：`/rag/api/v1/qa` 带 token + 客户端伪造 `X-User-Id: 999` → 上游收到
  `X-Username=u`（来自 JWT）、`X-Internal-Auth=证明`、**收不到 x-user-id**（剥离且不注入）、
  correlation-id 一致；无 token → 401。
- ⏸️ 与 RAG 后端 gateway 模式的**真实联调**待生产/联调环境（dev 模式 RAG 不验证明，故 dev 下
  行为与此前一致）。

## 5. 风险 / 已知遗留
- **身份对齐是数据前提**：office 登录用户的 username 必须在 RAG `user` 表存在，否则 RAG 401
  （fail-closed，正确行为）。长期解：统一用户源 / IdP（迁移设计 §2.4）。
- 全局剥身份头、多副本 LB、独立 IdP（JWKS+RS256）按迁移设计留后续。
