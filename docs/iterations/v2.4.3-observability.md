# v2.4.3 · 可观测 · 对账视图 · 预扣修正

> 2026-11-18 深夜 · 分支 `feature/2.4.3-observability` · 后端 **648 passed / 3 skipped** · 前端 **139 passed** · **未部署**
> 上一版 `v2.4.2`（上下文记忆重写）。

## 一句话

2.4.2 让账能对上、上下文不丢；2.4.3 让**每次模型调用可逐字回看**、预估准、对账有界面。

## P0 · 预扣估算修正

- 事实：`token_estimate_default=2000`，真跑实际 12,937（**偏低 6.5 倍**）——钱包被事后补扣、预算门失效。
- 公式重写：`estimate = max(2000, (本轮文本 token + 提示词固定开销 3000) × 平均步数 3.0 + 输出预留 2000)`
- 位置：`_stream_task` 内、`effective_text` **最终形态**（含记忆/产物索引注入）之后。
- 验证：预扣 11,342 vs 实际 13,424，**偏差 15%（<20% 达标）**。

## P1 · 账本对账视图

- 新接口 `GET /api/v1/admin/reconcile?days=7`：每行 `reserve / actual / settle / cache_read / expected`，
  自洽公式 `settle == actual − cache + ceil(cache × 0.25)`，不符 `ok=false`；预扣 < 实际一半标"预估偏低"。
- 管理端新 Tab「任务对账」：顶部汇总告警（不符条数/预估偏低条数）+ 明细表。

## P2 · LLM 调用级可观测（核心）

- 新表 `llm_call`（迁移 0016）：一行 = 一次模型调用（agent/step/model/**messages 脱敏**/原始输出/用量/耗时）。
- 记录点：`brain._with_overflow_retry` 成功后经 `call_recorder` 回调；graph 四处构造 brain 时注入
  （single / multi 子任务 / synth / 汇总官）。失败静默不阻断任务。
- 真跑样例（一次 3 步任务）：

```
step 1: data_analysis  输入 3,668  输出  69   1,121ms
step 2: data_analysis  输入 4,389  输出  32   1,133ms
step 3: data_analysis  输入 4,491  输出 145   1,591ms
```

- API：`GET /runs/{run_id}/llm-calls`（列表）+ `?detail=<id>`（单条完整，手机号脱敏）。
- 管理端：任务详情抽屉新增「模型调用」区块——点行看 messages 逐条 + 模型返回；可看工具 schema。

## P3 · 工具 schema 与回放入口

- `GET /api/v1/admin/tool-schemas?agent=...`：该 Agent 工具池的完整 schema（模型"应该"收到什么）。
- 任务详情抽屉内一键查看（与 llm_call 同区块）。

## 踩坑记录

1. **`_stream_task` 和 `tasks_stream` 是两个函数**——P0 第一版把估算插进了前者的作用域，
   引用后者的 `_estimate` 直接 NameError，5 个测试红。修正为独立公式（不依赖静态下限变量）。
2. **llm_call 表主键是 run_id 不是 task_id**（两表列名不一致），排查时写错列名浪费一轮。

## 没做的

- 预扣公式仍是常数假设（步数 3.0 固定）——更精确要按历史任务回归，收益边际。
- P5 游标分页/虚拟列表（trace 瘦身后 100KB 级，暂无必要）。
