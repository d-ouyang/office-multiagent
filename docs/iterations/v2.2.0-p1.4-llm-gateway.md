## 方案变更（对计划文档的重要修正，已与用户对齐）

原计划 B1 = 自托管 **LiteLLM Proxy 容器**。部署前服务器实况检查推翻了它：
3.6G 内存、available 仅 1.6G、**swap 已用满 1.9G**——给关键路径加一个 200~300MB
的新容器不可接受。调整为 **gateway（NestJS，现占 53MB）内置 LLM 代理路由**（+~30MB）：

- 调用面极窄（OpenAI 兼容 `/chat/completions` + tool_calls + 流式），`llm.py` 早已
  手写全部适配——LiteLLM 最值钱的 provider 适配层用不上，网关只需「按 model 路由 →
  换真实 key → 透传」；
- 归因（B2）与硬预算（B3）的收口点天然就在 gateway（JWT 身份已在）；
- 对 backend 两者外观一致（OpenAI 兼容端点），将来资源升级想换 LiteLLM 不返工。

## 三个真 bug（冒烟阶段抓到，全部修复）

1. **node:http 发不出 https 请求**：真实 provider 全是 https，`http.request({protocol:'https:'})`
   会静默挂到客户端超时——必须按协议选 node:https。e2e 假上游是 http 所以没暴露，
   是真容器冒烟抓到的。
2. **readBody 挂死**：main.ts 全局挂了 `express.json()`（代理纪律：显式 body parser），
   application/json 请求的流已被解析进 `req.body`，再监听 data/end 永远等不到 →
   401 之后的所有路径 45s 挂死。修复=优先 `req.body`，流读取仅作回退。
   这个 bug 同时解释了 e2e 4 用例挂起（supertest 场景同因）。
3. **容器互联端口写错**：`gateway:3001` 是宿主映射端口，容器互联必须 `gateway:3000`
   （Connection refused → decision-llm 回落规则）。
