## 为什么

上下文层此前只有"逐条截断 + 会话摘要"，六个上限散落在代码里、互不知情：

| 截断点 | 位置 | 值 | 可配 |
| ------ | ---- | -- | ---- |
| JSON 协议 history | `brain._render_history` | 24000 硬编码 | 否 |
| 原生 tool_calls | `brain._messages_for_tool_calls` | 24000 硬编码 | 否 |
| 工具观察摘要 | `react._summarize_observation` | 默认参数 24000 | 否 |
| 文档读取 | `config.doc_read_max_chars` | 50000 | 是 |
| 长期记忆注入 | `config.user_memory_inject_chars` | 4000 | 是 |
| 会话历史 | `memory.RECENT_ROUNDS` / `[:80]` | 4 轮 / 80 字 | 否 |

线上出问题时改不了、也说不清"这次上下文被谁吃了"。第一步先把它们收成可热更的开关，
不改变任何行为（缺省值与原常量逐一相等），只把"改得动"这件事先做到。

## 改动

- `core/config.py`：新增 `observation_max_chars` / `history_step_max_chars` /
  `history_recent_rounds` / `history_round_chars`，注释明确 **0 = 不限制**。
- `core/runtime_settings.py`：4 项进 catalog（scope=system + min/max + 中文说明），
  `public_items()` 自动带出，管理端无需改前端。
- `orchestration/react.py`：`_summarize_observation(max_chars=None)` 走运行时设置；
  0 时不截 content，也不加"已截断"标注（回退语义要干净）。
- `orchestration/brain.py`：新增模块级 `history_step_limit()`，`_obs_limit()` 与两个
  `staticmethod` 共用。**为什么不各读各的**：灰度期同一任务换协议就换截断行为，
  排障时无法归因。
- `orchestration/memory.py`：`prepare_turn(..., recent_rounds, round_chars)`；
  `recent_rounds=0` 走单独分支——Python 的 `rounds[:-0]` 是空列表，语义会静默反转成
  "全部原文保留"，测试 S-4 已锁死。

## 判据

`PUT /api/v1/settings/observation_max_chars=8000` → 同进程下一任务按 8000 截断并标注，
无需重启、无需发版。四个开关填 0 = 回到旧行为（回退路径）。
