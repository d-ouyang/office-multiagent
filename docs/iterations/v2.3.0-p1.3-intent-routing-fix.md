# v2.3.0-p1.3 · 意图路由三处修正（附带修复，非 C 层主线）

> 2026-11-16 · 分支 `feature/2.3.0-context-budget` · pytest 586 → **593 passed / 3 skipped**
> 起因：2.3.0 本地冒烟时撞到的既有缺陷——「文件就在目录里，模型却说读不了」。

## 事故链（日志原文）

提示「不要检索知识库。请直接读取文档文件 smoke-long.md」：

```
规则初判 = ['rag','analysis']        ← "检索"+"知识库" 命中，否定词不处理
决策小模型 = ['analysis']            ← 纠正成功
能力预检：文本含"知识库" → 要求 rag_retrieve
          analysis Agent 工具池没有它 → 改道 general（碰巧有 read_document）→ 成功
```

提示「请读 smoke-long.md，逐章列出每一章的报销上限」：

```
规则初判 = ['general']（0 命中）
决策小模型 = ['rag']，reason=查非结构化资料并以表格形式输出   ← 把"读文件"当成了查资料
primary = rag_retrieval，工具池 [rag_retrieve, render_flow, remember, recall, ask_user]
能力预检：guards 里没有"文件/文档"类词 → 不改道
模型如实说"我这边没有读取本地文档的工具，请上传文件" → ask_user
```

三条失败路径各断一处：**规则层**（否定词当肯定）、**模型层**（读文件≈查资料）、**兜底层**（guards 没有文件类词）。

## 已知局限（留给 2.4.0）

- **否定窗口是启发式**：8 字窗口、「勿」这类文言否定都靠枚举，长句里"我不觉得应该检索…"仍会漏。
- **guards 仍是手写映射**：每加一个工具/一种说法都要人肉同步，这次漏的就是"文件"。
  结构性解法是给 `intents` 增 `requires: [工具名]`，预检按 requires 判定，不再维护实体词表。
- **决策模型仍可能把"读文件"归到 rag**：prompt 里的反例是软约束，靠 N-3/N-4 的 guards 兜底。
- **文案未区分"能力缺失/信息缺失"**：模型仍可能说"没有工具，请上传"，而文件其实在。
  根治要先查目录再回话（`check_inside_base` 已有能力），归入体验待办。
