# 迭代总结 · v1.0.0-p1.2c — Alembic 迁移基线（任务 3）

> 对应计划：PLAN-1.0.0.md Phase 1 / v1.0.0-p1.2c（任务 3「db/init.sql → alembic 迁移基线」）。Tag：`v1.0.0-p1.2c`。本迭代完成 → **Phase 1 后端核心骨架全部收口**。

## 1. 目标
把 MySQL schema 纳入 alembic 管理：建立 alembic 脚手架 + 一条镜像 `db/init.sql` 的基线迁移，后续建表/改表走 `alembic revision`，不再手改 SQL。同时加**漂移护栏**保证基线迁移与 init.sql 始终一致。

## 2. 做了什么
- `backend/alembic.ini`：`script_location=migrations`，`prepend_sys_path=.`；`sqlalchemy.url` 仅占位，由 env 覆盖。
- `backend/migrations/env.py`：用 `app.core.db.DATABASE_URL` `set_main_option` 覆盖 URL（**单一真相源**：compose 服务名 / .env / 远端一致）；offline + online 两模式；基线为原生 DDL，`target_metadata=None`。
- `backend/migrations/script.py.mako`：新迁移模板。
- `backend/migrations/versions/0001_initial_baseline.py`：镜像 init.sql 全部 12 张表 + 种子（`CREATE TABLE IF NOT EXISTS` + `INSERT IGNORE`，幂等）；`downgrade` 逆序 DROP。
- `backend/tests/test_migrations.py`：漂移护栏（基线表集 == init.sql 表集）、种子在场、revision/down_revision 正确、env 覆盖 URL、模板存在。

## 3. 否掉的方案（最值钱）
- **不在 app 启动时自动 `alembic upgrade head`**：多副本同时启动会并发跑迁移（已知 footgun，锁表/重复 DDL）。迁移交给部署阶段一次性执行（Phase 7 deploy.sh 里 `alembic upgrade head`），app 只连库不建表。
- **基线不用 `op.create_table` 自动生成，而用原生 SQL 幂等写法**：与 init.sql 逐字一致，保证「compose 冷启动 init.sql 已建表」与「alembic upgrade」两条路可重复跑不冲突；代价是 downgrade 手写 DROP（可接受）。
- **不删 init.sql**：compose 的 mysql 首次启动靠它冷启动；删了就得在 entrypoint 里另跑 alembic，反而更脆。保留 + 漂移护栏测试兜底。

## 4. 验证
- `pytest backend/tests`：**30 passed / 3 skipped**（新增 `test_migrations.py` 5 例）。
- `alembic -c alembic.ini history`（offline，不连库）：`<base> -> 0001_initial (head)`，脚手架有效、revision 被识别。
- `py_compile` 全绿。
- ⏸️ 未对真实 MySQL 跑 `alembic upgrade head`（点5：DB 操作谨慎，交 compose up 后显式执行）。

## 5. 风险 / 已知遗留
- 基线为原生 DDL，后续如引入 ORM 模型再考虑 autogenerate（届时 `target_metadata` 接 Base.metadata）。
- `db/init.sql` 与基线迁移存在「双份」，靠 `test_migrations` 护栏防漂移；长期可在首个正式环境统一到「init.sql 只建库、表全走 alembic」。
- 迁移执行（upgrade）未纳入 CI/deploy，留 Phase 7。
