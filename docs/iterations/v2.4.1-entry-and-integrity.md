## 二、两轮真跑驱动的修复（本版主体）

### A. 多维图表卡片跑不通 —— 四层根因

表面报错是 `render_chart` 报"数值列不存在：metric_value"。剥开是四层：

1. `group_by` schema 只声明 `type: string` —— 代码早在 p1.13 就支持 ≤2 列数组；
2. **JSON 协议路径下模型只读得到工具 `description`，看不到 `parameters` schema** —— 改 schema 它根本没看见；
3. `data_analysis` 提示词没提多维分组，模型据此认为"只能单维度"，于是绕路导明细、越试越偏、开始编造工具名；
4. 模型输出的尾逗号 / 裸换行 / JSON 后带说明，一失败就整条任务终止。

修法对应四层：schema 改 `["string","array"]`、description 补数组说明、提示词补齐并禁止试探不存在的工具名、
`extract_json` 四层容错（全文 → 代码块 → 配平括号 → 去尾逗号）+ 解析失败日志带 `raw=`。

效果：**5/5 失败 → 2/3 成功**，成功时稳定只调 2 次工具。

### B. 结果截断 —— 五处叠加

用户反馈"多城市×月份分组会 truncated"。查下去真凶不是 top_n：

1. **`_limit()` 默认值写死 20** —— 不传 limit 的查询只回 20 行，比明细上限 50 还小。
   城市×月份真值 **66 组只回 20 组**，热力图漏掉 70% 数据而模型毫不知情；
2. `_limit` 内还硬卡 `min(_MAX_ROWS=50, ...)` —— 传 limit=200 也无效；
3. 分组与明细共用同一上限（分组行数 = 维度组合数，与明细行数量级不同）；
4. `db_query` **静默截断**：回 50 行不说还有更多；
5. `analyze_table` 的 `_MAX_GROUPS=100`：门店×月份 102 组会缺组。

修法：`aggregate_max_groups=500` 与 `db_query_max_rows=50` 分离；`_limit(raw, default)` 默认值由调用方给；
五处工具统一 `truncated` + `truncated_hint`；协议模板加"truncated 时先说明给了多少/共多少再下结论"。

效果：分组 **20 → 66 组（无截断）**，工具调用 4~10 次 → 2 次，终答从"请选择怎么办"变成直接给结论。

## 三、另外顺手修的两处

- `render_chart` 列名别名：`metric_value` ↔ `m_sum_pay` 互认，报错时直接告诉模型正确写法。
- `thought` 限长：协议加"≤80 字、禁止复述数据和字段清单"——真跑里它把推理写进 thought，越写越长直到输出截断。

## 四、四个教训（写给下一个自己）

1. **JSON 协议路径下，`parameters` schema 模型看不到** —— 能力说明必须同时写进 `description` 与提示词，改 schema 单点是无效功。
2. **默认值是最隐蔽的契约** —— `_limit` 那个 `20` 藏在 try/except 里，比显式的 50 更狠；限制类逻辑要测"不传参"的路径。
3. **YAML 缩进会让人白测一轮** —— general 段 8 空格、data_analysis 段 6 空格，用同一段文本 replace_all 只改到了一处。
4. **`raw=` 日志是排障分水岭** —— 没有它只看到"模型输出无法解析"，永远挖不到"它以为 group_by 只能单列"。

## 五、遗留

- 仍有约 1/3 概率走 ask_user 或 JSON 截断：`max_tokens` 是 8192 动态值（`min(8192, 剩余预算−prompt)`），
  thought 过长仍可能撑爆；下一步可在协议层强制 thought 短句 + 解析失败重试一次。
- 多维分组达 500 组上限时仍会截断（有 hint，但没法"全量看图"）；可考虑分页或 top_n 降维。
