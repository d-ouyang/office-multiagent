# 迭代总结 · v1.0.0-p6.4 — token 池真账 + /quota（任务 4/5）

> 顺序 1→2→4→3→5 之任务 4。Tag：`v1.0.0-p6.4`。p4.2 建的 token 池从"演练"变"真账"：
> /tasks 从登录身份取 user_id，reserve/settle 真实扣减，前端可见余额。

## 1. 做了什么
- `/tasks`：`effective_user_id = body.user_id or 登录身份 user["id"]`（body.user_id 仅保留给
  测试覆盖）；`estimate = body.estimate or settings.token_estimate_default`（2000 门槛值，
  LLM 用量事前估不准，settle 按真实 usage 补差——§十四 两段式闭环）。
- `TokenPool.recent()`：查 ledger 近 N 条流水（/quota 展示）。
- `GET /api/v1/quota`：余额 + 最近流水（受登录身份保护）。
- 钱包种子：init.sql `wallet (1, 100000)` + 现有库同值补种。
- `settle` 落账带 `model=settings.llm_brain_model`（账本可追溯模型）。
- 前端：侧栏用户面板显示余额（`.toLocaleString()`）；任务 done 后刷新余额；
  `quota_paused` 事件 → 警告条"余额不足已暂停（充值后自动继续）"。

## 2. 账本形态（澄清一个看错的"残留"）
`reserve` 落一行（settle=NULL）、`settle` 另落一行（reserve=reserved, settle=actual）——
**一条任务两笔配对**，是 p4.2 的原设计，不是残留。余额数学验证：
100000 − 2000(reserve) + (2000−3011)(settle 补差 −1011) = 96989 ✅。

## 3. 验证
- `pytest`：**129 passed / 3 skipped**（+2 /quota：余额/401）。
- **真链路**：任务前 100000 → 真 LLM 任务（rag 三轮检索）→ 任务后 **96989**（真扣 3011，
  与 settle 补差吻合）；ledger 两行配对（reserve=2000 / settle=3011, model=deepseek-chat）。
- 前端：tsc + vitest 21 + vite build 全绿；容器已重建。

## 4. 否掉的方案（最值钱）
- **estimate 不按 text 长度精算**：LLM 用量事前估不准是本质，门槛值（防超额并行）
  + settle 补差（真实账）才是两段式的意义；精算只是心理安慰。
- **不做充值端点**：充值=改余额=写操作，必须有管理端鉴权（§十三 管理角色），
  放进管理端批次（p6.x）；现在 dev 直接 SQL 充，文档写明。
- **余额不做实时推送**：done 后刷一次足够（账本位级变化，不需要秒级）；SSE 推送是过度设计。

## 5. 风险 / 已知遗留
- 充值端点/管理端（role=admin 门）未做——额度耗尽后目前只能 SQL 充。
- multi 子任务各自 reserve（并行）由原子 SQL 兜底防超额，但 estimate 是每子任务一份
  （父任务没预留总量）——复杂任务的额度保护粒度为子任务级，够用但非全局预算。
- token_ledger 的 model 列只记 brain 模型（不含子任务级差异）。
