## 三级硬预算的现状与补全

| 级别 | B3 之前 | B3 之后 |
|---|---|---|
| per-user | 钱包预扣（graph 内 quota_node，不足→quota_paused） | **入口 429 短路**：POST /tasks 时余额 < 预估直接拒绝（不启动编排、不预扣、不建任务行） |
| per-run | task_token_hard_limit（runtime_settings 可配）+ paused_budget | 不变（已达标） |
| per-tenant | **无** | **全站当日 token 预算**（runtime_settings 可配，0=关）：当日 ledger settle 总和达上限 → 入口 429；软告警在用量达比例（缺省 80%）时 webhook 一次（当日去重） |

边界说明：quota_node 保留在 graph 内——它是 resume 后重试 reserve 的兜底；入口短路只保护新任务（resume 有独立预扣逻辑，不复杂化）。

## 设计拍板

1. **429 在入口而非 graph 内**：不够扣的任务不建任务行、不进编排——资源保护前置；graph 内 quota_node 是续跑兜底，双层防线。
2. **日预算数据源 = ledger 的 settle 列**（B2 billed 口径）：预算约束的就是真实扣费口径，与钱包一致，无第二本账。
3. **日界为 UTC**（DATE(created_at)，引擎已钉 UTC）：与运维时区口径一致，文档注明"明日恢复"指 UTC 0 点。
4. **gateway 侧 user 归因再次裁剪**：调用链（llm.py 模块函数）无用户上下文，网关侧按 X-Request-Id 关联 backend trace（run_id→runs 表有 user_id）即可事后归因；实时 per-tenant 预算在 backend 入口做更简单且同样不可绕过（唯一的编排入口就是 /tasks）。
5. **告警 URL 通用 JSON**：企业微信/钉钉/Slack 各自格式差异在 url 侧挂转换服务解决，不内置多平台适配。

## 验证用例（部署后可复现）

1. **入口 429（per-user）**：把 test 账号 wallet 清到 100 → 发任务 → 应 429 `BALANCE_INSUFFICIENT`（且不产生 task 行）；充值后恢复
2. **入口 429（per-tenant）**：管理端（/admin 运行时设置）把「全站当日 token 预算」设为当前日用量 → 任何账号发任务 → 429 `TENANT_BUDGET_EXCEEDED`；设 0 恢复
3. **软告警**：配置 `BUDGET_ALERT_WEBHOOK_URL`（webhook.site 即可）→ 预算设为日用量 1.2 倍 → 发任务触发 → webhook 收到一次 payload（当日再发不再收）
4. **循环护栏**：管理端把「Agent 循环步数上限」设为 3 → 发一个多步任务 → 过程时间线第 3 步后出现「已达 max_iterations=3，强制给出阶段结论」
5. **回归**：预算 0（缺省）时全部行为与之前一致
