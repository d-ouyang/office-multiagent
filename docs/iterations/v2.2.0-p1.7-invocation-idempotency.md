## 目标（完成判据回填）

判据：**同一 run 重投 3 次 → 只 1 次副作用、1 次扣费**。
→ **达成**（本步覆盖副作用维度）：判据用例 `test_react_same_run_replay_executes_once`
——同一 run 两轮同工具同参数，副作用函数恰好执行 1 次（`calls == 1`），
第二轮观察来自已有结果；扣费维度由 C3 的 step 级进度落库配合（重复执行被

## 幂等键设计

**UNIQUE(run_id, tool_name, args_hash)**——**不含 step 序号**：
- resume 重放时步序可能漂移（护栏收尾/ask_user 插入会改变步数），结果级缓存对
  步序鲁棒；
- 「同 run 同工具同参数」结果理应一致——合法的重复查询也直接吃缓存（副作用只
  发生一次），与 react 重复护栏语义互补。

**三层防线**（执行一次的保证层层兜底）：
1. react 重复提示（prior≥1，把上次观察重新喂给模型，不执行）；
2. react 硬拦（prior≥2，hit_cap 强制收尾）；
3. **幂等缓存**（执行前 lookup 命中 → 直接复用观察；执行后 record 登记）。

## 设计拍板

1. **guard 是 callable 而非对象**：react 只依赖「可调用 + 可选 record 属性」，不引入
   表/引擎依赖——单元可测（Fake guard）。
2. **record 在 react 侧而非 repo 侧自动**：repo 是纯函数（lookup/record），何时登记是
   编排语义（成功且非哨兵才登记）——语义留在 react，存储留在 core。
3. **缓存观察存字符串**（str(obs) ≤24k）：ask_user 等 dict 哨兵不缓存（不可重放）。
4. **扣费维度**：重复执行消除后 settle 天然一次；C3 的 step 级进度落库将进一步
   收窄重跑范围（本步不动结算链）。

## 部署注意

- 部署时 CI 跑 `alembic upgrade head`（0014 建表，幂等 IF NOT EXISTS）；代码对
  表缺失已降级，**先部署代码后补迁移也不会炸**（顺序无耦合，但 CI 一起做）。
- 部署后验证：发任务 → `SELECT COUNT(*) FROM tool_invocation WHERE run_id=<run_id>`
  = 任务实际工具调用次数；对同一 task 重试/续答 → 计数不增、观察复用。
