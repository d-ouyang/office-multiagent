# 迭代总结 · v1.0.0-p6.18 — SQL 兜底护栏与按顺序展示过程

> Tag：`v1.0.0-p6.18`。

## 1. 目标
业务库查询不能靠提示词自觉。回复里的思考、工具和阶段回答按发生顺序分开，最后一段才是总结。

## 2. 做了什么
- `db_query` 仍是兜底：上传表、图表、知识库有专用工具时先用那些。查公司库时，SQL 必须带 WHERE、GROUP BY 或聚合，LIMIT 超过 50 会被压回 50，并加上 MySQL 的 3 秒执行提示。SQLite 把该提示当注释，测试不受影响。
- 这些限制写在工具实现和工具说明里。提示词只告诉模型什么时候才落到 SQL。
- 事件流按顺序切成思考、阶段回答、工具。最后一段正文显示在过程下面。过程默认收起，展开后每段思考再单独展开，高度固定、内部滚动。

## 3. 否掉的方案
- 不把「必须带 WHERE」只写进提示词。模型可以不理，整表扫描照样发生。
- 不把所有思考拼进一个框、所有正文拼进另一个框。推理模型和多步工具会交错输出，拼在一起就会一边想一边把半截回答露出来。

## 4. 验证
- `tests/test_tools_db.py` 与 `test_agents.py`：21 passed。无筛选的 SELECT 被拒绝，过大的 LIMIT 被压到 50。
- 前端 `deriveProcess` 与消息组件：阶段回答留在过程里，最后一段才出现在结果区。

## 5. 风险
- `ORDER BY` 加 `WHERE` 仍可能扫很多行，3 秒上限是第二道闸，不是索引保证。
- 历史消息如果整段正文都在工具调用之前发出，结果区会空，正文都在过程里。

## 6. 下一步
具名查询订单：按时间和地区等参数查业务库，不再让模型拼 SQL。
