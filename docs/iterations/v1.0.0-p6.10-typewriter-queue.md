## 1. 问题 1：observation 放大后 token 消耗——是，实测数据
| 任务类型 | 实际消耗（ledger 实测） |
|---|---|
| 普通问答（无文档） | 1.1K ~ 2.1K |
| 通读 2 万字文档（p6.9 后） | **25.1K**（2 条实测）|

原因：大文档 content 全量进 history，**多轮工具调用时每轮 LLM 请求都重复携带**。
**已知的优化路径（未实现，待用户点单）**：
1. **DeepSeek 上下文缓存**（前缀不变部分自动命中，缓存价约 1/10）——observation 追加在
   history 末尾、前缀稳定，天然友好；可在 usage 里核对 cache_hit_tokens；
2. **history 滑动窗口**：更早轮的大 observation 压缩为 200 字摘要，只保留最近 1-2 轮全量；
3. 同文件重复读取去重（已有"最多读 2 次"提示词约束）。

## 4. 问题 4：打字机渲染的真正解法——缓冲队列 + rAF 匀速播放
**为什么"每 delta 直接渲染"依然不逐字**：LLM 出字速度（~5ms/chunk）远快于屏幕刷新
（16.7ms/帧）——**到达即渲染时，浏览器每帧只显示最新状态，一帧合并 3+ 个 delta**，
物理上必然跳字。RAG 感觉逐字是因为其 delta 间隔恰好在帧间隔量级。
**正解（本轮实现）**：前端**打字机队列**——
- delta 到达只更新目标文本（textRef），**不触发渲染**；
- rAF 循环（60fps 恒定）每帧推进已显示位置：`step = ceil(剩余/8)`——
  LLM 出字快→匀速追赶，LLM 停→剩余 8 帧内逐字播完；
- markdown 每帧解析一次"已显示前缀"（marked 容错），渲染频率恒定与 delta 率解耦
  ——大文件频繁 delta 不再引发高频 DOM 重渲（性能与逐字感同时成立）；
- ≥20k 字解析走 Worker（既有 renderMarkdownSmart 阈值）。
旧的自适应节流（<2000 字每 delta 直渲）删除——队列方案统一覆盖。
