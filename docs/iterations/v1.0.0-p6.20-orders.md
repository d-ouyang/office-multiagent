# 迭代总结 · v1.0.0-p6.20 — 补齐模型能力并具名查订单

> Tag：`v1.0.0-p6.20`。

## 1. 目标
三个硅基模型按模型页标签补全。锅圈订单用固定参数查询，不让模型拼 SQL。

## 2. 做了什么
- LongCat-2.0：1.6T MoE 推理模型，1M，支持工具、前缀续写、长文本和 Vibe Coding。
- Hy4-preview：770B MoE 旗舰推理模型，1M，支持工具、前缀续写、代码、长文本和 Vibe Coding。
- Qwen3.5-9B：9B 推理模型，256K，支持工具和视觉。思考力度先不下发，避免参数取值不对导致请求失败。
- `query_orders` 只接受时间、订单号、门店、城市（上海/安庆）、状态、渠道、类型、履约方式、会员等级和分组。对不上的条件直接返回说明。列表最多 50 行。手机号、真实姓名和收货地址留在库里，不进工具结果。
- 表为空时从 `guoquan_orders_2025_2026_en.csv` 导入。已有数据不覆盖。

## 3. 否掉的方案
- 不把 DeepSeek-OCR 放进对话模型。它适合图片和扫描件转成文字的那一步，8K 装不下一轮办公对话。
- 不让订单走 `db_query`。筛选和汇总都写在 `query_orders` 里。

## 4. 验证
- 上海 1 月两条订单能筛出，分组实付能对上，未知状态被拒绝，电话不出现在结果里。
- 迁移和 init.sql 都有 `guoquan_orders`。

## 5. 风险
- 标了视觉的模型，对话请求目前仍只发文字。
- 导入只在表为空时发生。以后换一份正式订单，需要先清空或另做增量导入。

## 6. 下一步
做销售报表模板：时间范围、指标、口径和数据来源缺一项就不能当完成，数字必须来自 `query_orders`。
