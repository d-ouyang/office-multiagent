# 迭代总结 · v1.0.0-p6.11 — 钱包负余额保护（settle 下限保护）

> 修复 p6.9 实测发现的账务 bug：长文档通读等大用量任务把钱包余额穿成负数。Tag：`v1.0.0-p6.11`。

## 1. 问题
`TokenPool.settle` 的补差公式 `refund = reserved - actual`，当 **actual > reserved** 时
refund 为负，直接 `balance = balance + refund` 会把余额扣成负数。

根因分层：
- `reserve` 用原子 `UPDATE ... WHERE balance >= a` 只保证**预扣那一刻**余额够，
  不保证**实际用量**不超过预扣（如 p6.9 通读 2 万字文档，token 暴涨到 25.1K）；
- `settle` 没有任何下限保护，超支部分直接穿底。

p6.9 实测：余额 1000、预扣 1000、实际 3493 → 旧逻辑 `balance = 0 - 2493 = -2493`。

负余额的危害：
1. 破坏 `/quota` 前端展示（余额徽章显示负数）；
2. 后续 `reserve` 的 `balance >= a` 判定语义被污染（负余额下"余额不足"判定失真）；
3. 账务数据不可信。

## 2. 修复
`backend/app/core/token_pool.py` 的 `settle`：把 `balance + refund` 用 `CASE` 钳在 0。

```sql
UPDATE wallet SET balance = CASE
  WHEN balance + :r < 0 THEN 0 ELSE balance + :r END
WHERE user_id=:u
```

- 用 `CASE WHEN` 而非 `GREATEST`，MySQL 与 SQLite 两边都原子成立（测试用 SQLite 内存库）；
- `reserve` 侧已用 `balance >= a` 原子保护，余额不会在预扣阶段变负，**无需改动**；
- ledger 仍如实记录 `settle=actual`——下限保护只钳"可消费额度"，实际用量留痕供审计。

> 更彻底的修复是给任务加 token 硬上限（`actual <= reserved`，命中即硬中断），属 Phase 7 前的
> 成本治理（见 p6.10 §1 优化路径）。本轮只做"余额不得为负"的硬下限，最低成本止血。
