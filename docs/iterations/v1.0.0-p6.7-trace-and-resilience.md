# 迭代总结 · v1.0.0-p6.7 — 过程透明 + 失败可观测 + trace 落库 + 打字机优化

> 用户本地验证反馈 4 个问题的修复轮次（打字机不明显/过程不落库/上传位置/读文档任务失败
> 且过程不可见）。Tag：`v1.0.0-p6.7`。

## 1. 问题 4 根因与修复（最重要）
用户复现：上传 md → "读一下 dev/xxx.md 列出关键点" → LLM 幻觉 `action:"none"` →
CAPABILITY_MISSING → 跑偏 rag_retrieve → 再 none → "模型未给出有效动作或结论"空终止。
**三层根因**：
1. `step.observation = str(obs)` 把含 8000 字 content 的 dict repr 原样塞进 LLM
   上下文（给前端的 observation 才是 [:500]）——LLM 被垃圾上下文撑到"消化不良"；
2. 协议没有显式禁止 `action:"none"`/无效工具名；
3. 无效 action 直接终止，没有纠错与兜底。

**修复**：
- `react.py`：`_summarize_observation()`——进 LLM 上下文的是结构化摘要（关键字段 +
  content 截 1200 字 + "已截断展示"标注），不是 dict 全文；
- `react.py`：`Step.invalid_action` + **连续 2 次无效工具名 → 强制如实收尾**
  （列出已完成步骤，不空转跑满 10 步）；
- `brain.py`：协议显式"action 只能是清单内名字，禁止 none/null；总结类任务直接写
  终答"；JSON 包装的 final 不再走"未给出有效动作"路径；
- `agents.yaml` general：补"read_document 同一文件最多 2 次"+"总结类任务不调工具"
  （真跑见证修复前 read_document 被调 8 次，修复后 **1 次**）。

## 2. 问题 2：过程落库（trace）
- 迁移 0003：`message.trace MEDIUMTEXT`（JSON 事件数组：thinking/tool_call/
  observation/status/content_delta 全量）；
- worker 落库时随 assistant 消息写 trace；`GET /sessions/{id}/messages` 返回 trace；
- 前端 selectSession/初始加载按 trace 重建 events → **复用现有折叠面板+markdown 渲染**
  （深度思考/步骤折叠、终答 md），刷新/切会话不丢失；
- **真跑见证 + 自愈**：trace 首版因 worker 里 `json.loads`（只 import 了 `_json`）
  NameError 静默失败（消息落库但 trace NULL）——正是用户抱怨的"失败不可见"同类病根！
  修复后落库异常改为 **ERROR 级 + 注释警示**（流照常结束，但日志必须醒目）。

## 3. 问题 1：打字机逻辑说明 + 优化
**当前显示逻辑（用户问的）**：
- LLM 自然语言终答：每个生成 chunk 到达即 `content_delta` 直推前端（**真逐字**，
  速度=LLM 出字速度；p6.3 实测 173 个 delta 连续 1-2ms）；
- LLM 偶尔仍用 JSON 包装 `{"final": ...}`：**旧行为一次发全**（"突然全部返回"的来源）。
**优化（本轮）**：JSON final 路径改为 **5 字/块切片推 + 12ms/块间隔**（`Step.chunked`），
视觉与自然语言路径一致；自然语言路径本就是真流式无需改。
**后续可调**：块大小/间隔是常量（react.py `text[k:k+5]` / `sleep(0.012)`），
想更慢可调大；或把切片逻辑也改成"按 LLM chunk 到达推"（需协议层彻底禁 JSON final）。

## 4. 问题 3：上传位置/引用文件——方案（实现排 p6.8）
**浏览器安全限制**：web 页面无法像 WorkBuddy（桌面端）那样直接引用本地文件路径，
只能"上传到服务器"或"选择已上传文件"。方案：
1. 上传入口从输入条旁移到**输入框上方的附件区**：选中/拖拽文件 → 上传 →
   以 chip 形式显示（📎 dev/xxx.md ✕），可删除；
2. 发送时附件名随消息走：`/tasks` 收 `attachments: string[]` → 后端注入 prompt
   前缀"【附件】dev/xxx.md，请优先 read_document 读取"；
3. 附件 chip 随消息持久化（message/task 记录），历史可见；
4. 输入区支持拖拽（dragover/drop）——接近 WorkBuddy 的交互心智。
