# 迭代总结 · v1.0.0-p4.2b — 与 RAG 同机共存：端口去冲突（compose）

> 对应：Phase 4 整合（本机 `docker compose up` 后发现）。Tag：`v1.0.0-p4.2b`。应用代码未改，单测仍 65 passed。

## 1. 目标
office-multiagent 与 rag-qa-system **同机共存**，消除 Docker 端口冲突，让 office 全栈稳定跑起来。

## 2. 发现的问题（本机实跑暴露）
- RAG 的 **FastAPI 是宿主进程**，占 `127.0.0.1:8000`（`企业级RAG智能问答系统 v4.0.0-p4.10`）；RAG 的 **NestJS 网关也是宿主进程**，占 `127.0.0.1:3000`（`rag-qa-gateway v2.0.0-p0.2`）；另有 `rag-mysql/redis/chroma` 占 `127.0.0.1:3306/6379/8001`。
- office 同名宿主端口被**遮蔽**（`curl localhost:8000/3000` 打到的是 RAG）；更严重：office 的 `mysql/redis/chroma` 因宿主端口（3306/6379/8001）发布冲突**被踢出 office-net**，导致 backend 曾 `Name or service not known`（degraded）。

## 3. 修复（docker-compose.yml）
- **去掉 office `mysql`/`redis`/`chroma`/`backend` 的宿主端口映射**：中间件与后端仅内网（符合设计 §12.3 容器独立 + §13.3「后端只内网可达，网关才是入口」），经 office-net 服务名互访——既去冲突又更安全。
- **office `gateway` 宿主端口改 `3001`**（容器仍 3000，前端 nginx 走容器网络 `gateway:3000` 不受影响），避开 RAG 的 3000。

## 4. 验证（本机实跑）
- `office-net` 现含**全部 6 个容器**（frontend/gateway/backend/mysql/redis/chroma）。
- backend `/api/v1/health` **全绿**：mysql/redis/chroma 全 `ok:true`。
- 前端 `:8080` HTTP 200；经 `:8080/api/v1/demo/stream`（nginx→office-gateway→office-backend）NDJSON 正常流出。
- 宿主 `:3001/api/health` → `office-multiagent-gateway`（不再是 RAG）。
- RAG 各服务（FastAPI 8000 / 网关 3000 / rag 中间件）**均不受影响**。

## 5. 最终端口（office-multiagent）
| 服务 | 宿主端口 | 说明 |
|---|---|---|
| frontend | **8080** | UI 入口 http://localhost:8080 |
| gateway | **3001** | API 直连入口（可选） |
| backend | 无（内网） | 经 8080/3001 访问；§13.3 内网 only |
| mysql/redis/chroma | 无（内网） | backend 经 office-net 服务名访问 |

## 6. 已知遗留 / 下一步
- backend 不再暴露宿主端口 → 如需 office 的 `/docs`（Swagger），临时在 `.env` 设 `BACKEND_PORT=8002` 之类空位即可（默认不暴露，保安全）。
- 前端「开始演示」走公开 `/api/v1/demo/stream`；`/tasks` 等需 JWT（登录态后续）。
- 下一步 Phase 5 办公能力池。
