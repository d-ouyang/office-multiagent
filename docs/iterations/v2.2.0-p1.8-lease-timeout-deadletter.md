# v2.2.0-p1.8 · lease / run 硬超时 / 死信（Phase C2）

> 2026-11-14 · 分支 `feature/2.2.0-harness` · pytest 547 / gateway jest 52

## 三件事

### 1. run_id lease（同 run 单执行者）
`runs.register` 从「无条件覆盖」升级为 **lease 语义**：该 run 已在跑 → 返回 None。
- 主入口（/tasks）：worker 启动**前**预检 → 409 `LEASE_CONFLICT`（双击发送/重试赛跑不再双跑——幂等表挡工具副作用，挡不住 LLM 调用与预算双花）；
- 三处 resume worker：线程内发现冲突 → 流内 error 事件（`LEASE_CONFLICT`）+ 收尾；
- **单机单进程下内存表即真锁**；多副本部署时升级 MySQL GET_LOCK（连接级、需专用连接持有全程），调用方接口不变——已注释入码。

### 2. run 级硬超时（watchdog）
worker 启动 `threading.Timer(run_hard_timeout_seconds=900, cancel_ev.set)`，到点置位取消事件 → 编排走**协作取消**收尾（paused_user + settle + 事件流完整）；正常完成 finally 里 `watchdog.cancel()`。防任务挂死占住 worker 线程（此前无总时长上限，db_query 有 SQL 级超时但编排整体没有）。

### 3. 死信（编排异常不再静默断流）
worker 兜底 except 此前只打日志——任务异常后用户端流直接断、无任何痕迹。现在：
- 用户收到 **error 事件**（`RUN_DEAD_LETTER`，带 B2 归因字段）；
- 落**审计** `run.dead_letter`（动作白名单已加，管理端按动作筛可查，error 截断 500 字）；
- 登记失败不影响流收尾（双层 try）。

## 设计拍板
1. **内存 lease 先行**：单机部署下 GET_LOCK 是纯开销；接口不变，多副本时内层替换实现（runs.py 注释即 TODO）。
2. **watchdog 用协作取消**而非强杀线程：线程无法安全强杀；取消事件让编排走既有收尾链（settle/落库/事件），账实相符。
3. **死信落审计而非 task 表**：失败不落 task 行是既有设计（避免重跑重复对话）；审计表 append-only + 管理端已有查询面，零新表。
4. **重试计入预算核实结论**：LLM 层重试（429/网络）失败无 usage、成功一次结算——provider usage 天然正确；工具重试的副作用风险已由 p1.1 告警 + C1 幂等表覆盖。无需改动。

## 测试（tests/test_lease_guard.py +4）

- watchdog 到点置位取消事件；
- **死信判据**：run_task 抛未接住异常 → 用户收到 error 事件（code=RUN_DEAD_LETTER、trace_id 归因随行）+ 审计白名单登记；
- lease 占住期间全部拒绝（入口依赖行为）。

## 部署后验证用例
1. **lease**：发任务后立即对同一会话再发一条 → 新任务正常（新 run_id）；对**运行中**任务的 resume 双击 → 流内收到 LEASE_CONFLICT error
2. **watchdog**：管理端把 `run_hard_timeout_seconds` 临时改小（或 .env 设 30）→ 发一个会超过时限的任务 → 走 paused_user 收尾、钱包 settle 正常
3. **死信**：无人工故障注入路径——单测覆盖（test_dead_letter_emits_error_event_and_audit）；生产观察点 = /admin 审计日志按 `run.dead_letter` 筛
