# v2.3.0-p1.2 · 上下文超限兜底（C 层补全收尾）

> 2026-11-16 · 分支 `feature/2.3.0-context-budget` · pytest 581 → **586 passed / 3 skipped**
> ⚠️ **未部署**（本地已提交，未打 tag）

## 为什么

p1.1 的预算器假设"我们自己算准了就够"。但 provider 的 tokenizer 与 `estimate_tokens`
（CJK 1:1、其余 4:1）不可能完全一致——差 5~10% 很常见。一旦实际比估算大，请求就是
**400 context_length_exceeded**，而 `llm.py` 此前把它当普通 4xx：不重试、直接上抛，
brain 兜成"模型暂不可用"，用户看不出是自己文档太大，只会来问人。

预算器负责"尽量不撞"，本步负责"撞了能自己爬起来"。

## 机制

1. **独立异常类** `ContextOverflowError(LlmError)`：它是**可恢复**错误，必须与
   "网络抖动"（可重试）和"参数写错"（不可重试）区分开。
2. **识别**：`status in (400, 413)` 且 body 命中措辞白名单（`context length` /
   `maximum context` / `上下文长度` / `输入过长` 等 13 条，中英混合）。
   为什么用白名单而不是裸 `超出`：会把"超出配额""余额不足"误判成溢出，然后压缩重试——
   用户等更久，错误一样。
3. **排除出瞬时重试**：`_is_transient` 显式返回 False。否则会按 4xx 规则…（现状是直接抛）
   或按 5xx 规则重试三次，输入没变、拒绝也没变，纯烧钱。
4. **压缩重试一次**：`brain._with_overflow_retry(call, build, budget)`——catch 到溢出就用
   `budget // 2`（不低于 1000；原本不限则给 4000）重建 messages 再调一次。三条路径
   （JSON 非流式 / JSON 流式 / 原生 tool_calls）都接；流式可以安全重放，因为 400 在
   首块之前返回，此时一个 chunk 都还没推给用户。
5. **失败文案**：两次都溢出时返回"内容超出模型一次能接收的范围（已自动压缩一次），
   建议把文档拆小"，**不把 provider 原文丢给用户**。

## 关键决策

- **只重试一次**：压缩有损，连压两次的收益远小于"如实失败 + 给可操作建议"；也避免
  provider 持续拒绝时把预算烧光（与 p1.2 之外的循环护栏同一思路）。
- **压缩力度腰斩**：压太狠模型会"忘掉"已查过的数据，重试成功也答不对——腰斩是"再给一次
  机会"，不是"保证过"。
- **reservation 不重算**：第一次按大 messages 预占、第二次用小 messages 复用同一笔占位，
  偏保守（多占不退），不会导致超支。

## 测试（tests/test_context_overflow.py，5 条）

O-1 识别中英措辞 + 业务 400 不误判 + 5xx 不算溢出 / O-2 不入瞬时重试（429 对照组仍可）/
O-3 首次溢出→压缩→成功，且第二次 messages 更短 / O-4 两次都溢出→只调 2 次 + 可操作文案 /
O-5 预算原本不限时给 4000（否则重试等于没压）。

## 已知限制

- 若 provider 先推了 chunk 才报错（罕见，通常 400 在响应头就返回），流式重试会重复输出。
  当前不处理：这类错误几乎都由请求头阶段拦截；真出现时前端会看到重复片段，但不影响正确性。
- 识别依赖措辞白名单，新 provider 可能漏判 → 表现为退回旧行为（"模型暂不可用"），
  不会误伤别的错误。加一条 hint 即可，不需要改逻辑。
