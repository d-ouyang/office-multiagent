## 一、轻量结果校验器（终答数字对账 observation）

### 定位（轻量三不原则）
**不新增 LLM 调用、不阻断任务、不重跑**。终答产出后把数字与本次工具观察（含任务原文）
对账，对不上的如实标注（observation 事件 + WARNING 日志），判断权留给用户。

### 误报压制（只校验"硬数字"）
| 数字类型 | 处理 | 理由 |
|---|---|---|
| 整数 ≥1000 或带小数 | 参与对账 | "32,926 元""85.2%" 这类口径数字编造代价高 |
| 小整数（"3 点建议""第 5 行"） | 忽略 | 到处都是，对不上不说明编造 |
| 任务原文里的数字 | 计入来源池 | 用户自己给的，终答引用合法 |
| 一次工具都没调的终答 | 跳过（skipped） | 模型凭提示词作答，无从对账 |

数字归一化：千分位逗号、万/亿量词（允许空格）、小数尾零（"1.20 万"=="12000"）。
实现注意：**不用 `%g`**（只保 6 位有效数字，7 位数会变成 1.23457e+06 破坏对账）。

### 接入点
- `single_node`：对 `run_react` 的终答 vs 其 steps 的观察对账，label=`single:<agent>`。
- `multi_node`：每个子任务终答各自对账（观察取子任务自己的 steps），label=`multi:<key>`。
- 对不上 → `observation` 事件（tool_id=`result_validator`，文案带「可能为模型推断或笔误，
  请注意核对」）+ WARNING 日志；事件随 trace 落库，历史重建可见。
- `run_task` 结果新增 `validation` 字段：`{"checked": n, "unmatched": [...]}`（None=跳过/未校验）。
- 开关：`RESULT_VALIDATION`（默认 true）；校验器自身异常一律吞掉（不外溢、不阻断）。

### 文件
- 新增 `app/orchestration/validator.py`（纯函数 + `check_and_report` 回调式接入）。
- `graph.py`：`_validate_and_flag()` helper + single/multi 出口挂接。

## 二、显式长期记忆（user_memory，用户可查可删）

### 设计要点
- **显式**：只有用户明确要求"记住 XX"（或自己在前端添加）才写入；工具描述里写死
  「只有用户明确要求记住时才调用」。误写用户随时可删。
- **只增不改**：没有 update 接口；删除即物理删（用户要求"忘掉"就该真的没有）。
- **满了如实拒绝**（不静默淘汰最旧的）——静默丢失比报错糟糕；每用户上限
  `USER_MEMORY_MAX_ITEMS`（默认 100）。
- **去重幂等**：同用户同内容不重复写，返回已有行 + `duplicated: true`。
- **越权同形**：删别人的记忆返回 404（不泄露存在性）。

### 数据层
- 迁移 `0011_user_memory`：`user_memory(id, user_id, content VARCHAR(512), source
  agent|user, created_at)`；无 update_time/deleted_at；KEY idx_user_memory_user。
- `app/core/user_memory_repo.py`：`add/list_for/delete/count`；`MemoryFull` /
  `ContentTooLong` 异常；`db/init.sql` 同步。

### Agent 工具（仅登录用户挂载）
- `remember(content)`：写入长期记忆；满了/超长如实报错（ToolRegistry 兜成错误观察）。
- `recall(keyword?)`：查询记忆；**关键词没命中 ≠ 没有记忆**，note 里如实区分。
- 挂载：`build_default_registry(user_id≠None)` 时注册；白名单加给 general /
  rag_retrieval / data_analysis / report_generation（agents.yaml）。匿名场景工具不可见。

### 每轮注入（routes._stream_task）
- 取用户最近 `USER_MEMORY_INJECT_LIMIT`（默认 20）条，拼「【用户长期记忆】…」块
  到任务文本前部；同时 `context_parts["memory"]` 计入 context_usage 的 memory 分栏
  （前端用量环可见）。查库失败不阻断任务（记忆是增强，不是依赖）。

### 用户 API
| 端点 | 行为 |
|---|---|
| `GET /api/v1/memory?keyword=` | 我的记忆列表（新的在前） |
| `POST /api/v1/memory` | 手动添加（source=user；空/超长 400、已满 409） |
| `DELETE /api/v1/memory/{id}` | 删自己的；别人的/不存在一律 404 |

### 前端（个人中心新增"长期记忆"视图）
- `AccountPanel` 加 Brain 图标入口：列表（内容 + 来源标签 + 时间）+ 添加（textarea ≤300 字）
  + 单条删除；错误条复用 account-err。`api.ts` 新增 `listMemory/addMemory/deleteMemory`。

## 真机验证
- `docker compose up -d --build` + `alembic upgrade head` → `0011_user_memory (head)`。
- 登录 → 添加记忆 → 列表 → 删除全链路（Playwright 截图）。
- 对话说「记住 XXX」→ remember 工具落库 → 下一轮注入可见（context_usage memory 分栏）。
- 终答编造数字场景 → result_validator observation 出现在过程面板。

## 遗留 / 边界
- 校验器只对账数字：单位换算（"半天"="4小时"）、文本结论冲突不在此版范围。
- 记忆注入为"全量最近 N 条"，不按当轮问题语义检索（Chroma 语义检索留作后续增强）。
- recall 用 LIKE，非语义检索——够用，用户量级小。
