## 一句话

2.4.4 让访客免账密进门；2.4.5 修两个"看起来像挂了"的真问题：**任务停住后界面永远弹同一张问题卡**，
和**模型首字迟迟不来时界面完全静止**。

---

## 现象

线上 `office.nianan.site`（同事两个会话都触发过 `ask_user`）：

1. 会话列表里任务"应该都结束了"，但两个会话一直挂着侧栏「待确认」徽章；
2. 刷新后每次都弹同一张补充输入卡（截图里那张日期范围问题），点「跳过」当时收起，刷新又回来；
3. 用户最初的报障是"`POST /api/v1/tasks` 卡住了一直不动"，curl 复现三次：**12.3s / 39.1s / 78.1s**，
   全部 200 + 完整 NDJSON，末尾 `done{status:"paused_input"}`——没挂，是慢 + 反问。

## 根因（四条，都不是"会话互相阻塞"）

| # | 根因 | 证据 |
| - | ---- | ---- |
| 1 | **`task` 行是"跑完才 INSERT"**，用户等不及重发不会回收旧的 `paused_input` | `SessionRepo.record_task` 只在 worker 收尾时调用；线上一个会话堆了 3 条 `paused_input` |
| 2 | **侧栏徽章是 `EXISTS(会话内存在 paused_input)`** | `session_repo.list_sessions` 原 SQL 无"最新一条"约束 |
| 3 | **刷新横幅是"最近 10 条里 `find` 任意 paused"** | `api.ts:latestPausedTask` 用 `tasks.find(...)`，跳过最新那条 `done` 继续往下找 |
| 4 | **「跳过」只改本地 state，不落库** | `AskUserCard.onDismiss` 只 `setPaused({dismissed:true})` |

**会话隔离结论：没有问题，也不存在互相阻塞。** 三层证据：
读写全部按 `session_id` / `user_id` 过滤；每个 run 的 lease 是 `run_id` 级的（`core/runs.py` 内存字典，
不同 run 不抢锁）；LangGraph 的 checkpoint 线程 `thread_id = run_id`（不是 session_id），
`/tasks/{id}/answer` 显式带 `task_id`、校验 `paused_input` + 归属。
两个会话同时挂起 `ask_user` 各自独立——复现时我在同一会话连开 4 个 run 也互不影响。

**为什么会"慢到像卡死"**：上游 `deepseek-v4.1-flash`（硅基流动）首 token 静默实测 **29s / 54s**，
这段时间响应里一个字节都没有；`httpx` 的 read timeout 只在两个 chunk 之间计时，对"首字不来"不兜底；
单轮 700+ 个 thinking chunk 一 token 一条推，总耗时 40~90s。

## 改动

### P0 · 状态机收敛（后端）

- 新状态 `superseded`（已作废）：语义上是**终态**，不参与 `LIKE 'paused%'` 口径，
  管理端「暂停数」不再被僵尸行虚高。
- `SessionRepo.supersede_session_paused(session_id)`：会话里所有 `paused_input` → `superseded`，`pause_reason` 清空。
  **触发点**：`_stream_task` 拿到 lease 之后（被 409 挡掉的重复请求不动状态），即"新任务一发出，旧暂停作废"。
- `SessionRepo.supersede_task(task_id)`：单条作废，只接受 `paused_input`（终态不许改写）。
- `has_pending_input` SQL 加"必须是该会话最新一条任务"约束（防御存量脏数据）。
- `POST /tasks/{id}/answer` 新增 `action: "skip"` → `superseded`；非 `paused_input` 返回 409。

### P1 · 流式心跳（后端 + 前端）

- 新事件 `EventType.HEARTBEAT`（`data = {elapsed_s, phase}`），seq 从 `10^6` 起——
  绝不与 run 自身序列抢号（前端 `derive` 按 seq 排序）。
- `_start_heartbeat(q, run_id, stop_ev)`：每 `heartbeat_interval_seconds`（默认 3s）一帧，
  worker 收尾时**先停心跳再投哨兵**（心跳不许落在 `None` 之后）。接在 `/tasks` 与 `/tasks/{id}/answer` 两条主流。
- 前端：`ChatMessage` 的流式占位从"正在思考…"变成"正在思考… 已等待 12s"，
  由最后一帧心跳的 `elapsed_s` 驱动（`liveMessages` 内联计算，不进 derive 分段）。

### P2 · 首 token 超时（后端）

- `SilentStreamWatchdog`：N 秒（默认 45s）内一个字节都没来 → 从旁路线程关掉响应，
  把阻塞中的 `iter_lines` 打断成 `httpx` 错误；已收到首个 chunk 立即失活。
- 关流后归入既有"首块前瞬时失败"重试链路（`_is_transient` 认 `Timeout`），
  错误文案 `LLM 首 token Timeout：45s 内未吐任何内容`。
- 已出字后不重试（重复输出比失败更糟，沿用原纪律）。

### P3 · 前端「待确认」

- `latestPausedTask` → **只认 `tasks[0]`**（服务端已按 `created_at DESC`）。
- 「跳过」→ `POST /tasks/{id}/answer {action:"skip"}`，落库后再收起。
- 管理端：`STATUS` 加 `paused_input=待确认` / `superseded=已作废`，任务筛选加「已作废」。
