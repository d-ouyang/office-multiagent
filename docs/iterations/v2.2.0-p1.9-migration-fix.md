## 1. step 级进度落库——核实结论：已被 C1 实质覆盖，不造重复轮子

原计划「step 级进度落库收窄重跑范围」逐项核实：
- **副作用零重复**：C1 幂等表已存每次执行的观察（observation ≤24k），重跑节点时
  逐步命中缓存（工具不重执行）✔；
- **观察可复用**：resume 的 prior_steps 回放机制已有（2.1.0 P1-1）✔；
- **LLM 决策重跑**：非副作用（重新决策≠重复花钱的错误——决策输入相同但 provider
  计费按次，重跑确实重烧）——但 ReAct 步骤的 LLM 调用无法用「结果缓存」去重
  （决策非确定性），真要节点内恢复需 LangGraph 节点内 checkpoint（架构不支持，
  同步 invoke 单节点无中间快照）。
**拍板**：副作用安全已闭环（C1），LLM 重烧是理论损失（幂等表命中后重跑很快——
工具全走缓存，只重烧决策 token）；为边际收益引入节点内 checkpoint 机制不值，
**跳过，记入文档**。

## 2. 0001 迁移多语句 bug 修复（建库流程闭环）

**问题**：0001 的 upgrade 是单个多语句 op.execute（13 CREATE + 3 INSERT 一个字符串）
——MySQL 单次 execute 不允许多语句 → **纯 alembic 全新装必炸**，生产一直靠
「init.sql 灌库 + `alembic stamp 0001`」绕过，init.sql 列级护栏由此而来。

**修复**：upgrade 拆为 **15 个逐语句 op.execute**（12 CREATE + 3 INSERT，语句内容
与 db/init.sql 保持不变——护栏测试防漂移继续有效）；已 stamp 的生产库不受影响
（0001 不会重跑）。

**护栏**：`test_0001_single_statement_per_execute`——静态断言 0001 每个 op.execute
不含分号分隔的多语句，防止将来再合入大块。

**端到端验证**（本地 backend 容器 + 临时空库 alembic_verify）：
```
alembic upgrade head  →  0001→…→0014 全链跑通
20 张表建成、alembic_version = 0014_tool_invocation
```
纯 alembic 建库从「必炸」变为可用——**生产建库流程闭环**（init.sql 路径保留，
alembic 路径成为可选替代，两者由护栏测试锁定同构）。
