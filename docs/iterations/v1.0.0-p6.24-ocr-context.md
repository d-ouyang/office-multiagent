# 迭代总结 · v1.0.0-p6.24 — 扫描识别、短期记忆和上下文用量

> Tag：`v1.0.0-p6.24`。

## 1. 目标
没有文字层的文件能读出字。每个会话能看见上下文用了多少，并且带上短期记忆和更早对话的压缩。

## 2. 做了什么
- `read_document` 增加 png、jpg、jpeg、webp。PDF 文字层够用就直接抽。不够用时抽出前 3 页图片，交给 DeepSeek-OCR。这个模型不进对话列表。
- 测试文件：`backend/tests/fixtures/text_layer.pdf`（文字层，内容是 nianjia policy）、`scan_slip.png` 和 `scan_page.pdf`（页面上写着「锅圈食汇 上海店 实付 128.50 元」）。同一份也放在 `data/upload/dev/`，方便在界面里点开。
- 最近 4 轮问答留在「近期对话」。更早的每轮只留问和答各 80 字，放进「历史摘要」。本轮如果出现这个、那个、它、刚才、上面，会要求只按这段上下文确定指代。
- 会话标题右侧是上下文环。总量是当前模型的上下文窗口，用量是各栏估算相加。点开能看到系统提示、工具说明、规则、历史摘要、近期对话、本轮问题。历史摘要这一栏就是压缩后的部分。

## 3. 否掉的方案
- 不把 DeepSeek-OCR 放进对话模型。它只有 8K，只适合这一小步。
- 超大文件分段、知识库带当前用户和依据校验，这次不做。
- 复杂任务已经能按依赖分成前后层，但同一层仍是一个接一个执行，下一步也还没把上一步的结果传过去。这次不改调度。

## 4. 验证
- 6 轮历史里，最近 4 轮留在近期，前 2 轮只出现在摘要。
- 文字版 PDF 不调用识别。扫描版 PDF 文字层为空，会调用识别。
- 编排接口在补上消息表字段后仍能流出 NDJSON。

## 5. 风险
- 用量是按字估算的，不是接口返回的 prompt token。汉字按 1 个 token，其余大约 4 个字符 1 个 token。
- 容器里没有中文字体。测试图是在生成时用宋体画好的。识别效果取决于 DeepSeek-OCR 当时是否可用。
