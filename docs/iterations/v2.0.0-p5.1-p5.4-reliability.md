# v2.0.0-p5.1 ~ p5.4 · 执行器可靠性加固（重试 / 失败隔离 / 持久化续跑）

> 分支 `feature/2.0.0-p5-reliability`（自 `feature/2.0.0` 切出）。
> **本工作包未打 tag、未部署**：打 `v*` tag 即触发 CI 自动部署生产（p6.47b），按用户要求全程只在本地分支推进。
> 测试：基线 **438 passed / 3 skipped** → 本包后 **460 passed / 3 skipped**（净增 22，零回归）。

## 1. 背景：为什么做这四件事

源自一次「自研执行器 vs LangGraph」的代码级盘点。结论是两者不在同一维度：

- **Agent 行为质量**（观察摘要化、三道护栏、逐步 token 计量、双协议、NDJSON 事件语义、DAG 确定性）——自研已做得比框架通用实现更细，**不动**。
- **运行可靠性**（重试覆盖面、失败隔离、持久化与恢复）——框架有而我们缺，**本包补这四项**。

因此本包是**纯增量加固**：不改 `TaskState` 字段与合并语义、不改 NDJSON 事件形状、不换 ReAct 循环与 DAG 调度、不引入 LangChain Tool 层或 LangSmith。

## 2. 实施前的两处判断修正（留痕，避免误导后来者）

盘点阶段有两处结论在动手读码后被推翻，计划文档已同步更正：

1. **「LLM 调用零重试」不成立。** `core/llm.py` 的非流式 `chat` 与流式 `chat_stream` 自 p6.7b 起就有 3 次尝试 + 退避，流式还有「已出字（`emitted_any`）不重试」防重复输出；`brain.py` 里的 `except LlmError` 只是**重试耗尽之后**的降级，不是"没有重试"。真实缺口是 **429 与 500 不在可重试集合内**，且重试参数硬编码。p5.1 据此重写。
2. **「本地 venv_test 未装 langgraph」是探测方法错误。** langgraph 是 namespace package，`__file__` 为 `None`，早先脚本 `os.path.dirname(langgraph.__file__)` 抛 `TypeError` 被误判为未安装。实际 `.venv_test` 内为 **langgraph 1.2.16 + langgraph-checkpoint 4.3.0**，与生产一致。只有 `langgraph-checkpoint-sqlite` 确实未装。

## 3. p5.1 · LLM 重试补 429/500 + 参数配置化

**问题**：`_is_transient` 只做字符串匹配，覆盖 `ConnectError/Timeout/.../502/503/504`，**429 与 500 完全不重试**。而 multi 层内并行（`dag_max_concurrency=3`）多个子任务同时打同一模型时，限流 429 恰是最需要退避重试的场景——一次 429 直接把已跑 N 步的子任务降级成「模型暂不可用」。同时 `range(3)` 与 `0.8*(attempt+1)` 硬编码在两处循环里，生产无法调整。

**改法**（`core/llm.py`、`core/config.py`）：

- 可重试判定升级为「**状态码结构化判定 + 网络错误字符串兜底**」：新增 `_status_code_of()` 从 `LLM 返回 <code>: <body>` 提取状态码，`_TRANSIENT_STATUS = {429, 500, 502, 503, 504}`；401/400 等其余 4xx 维持不重试。
- 新增 `_retry_delay()`：**429 用独立且更长的退避基数**（限流要等服务端窗口，与网络抖动不同量级）。
- 新增配置：`llm_max_retries=2`（总尝试 3 次，与现状一致；0 可完全关闭）、`llm_retry_backoff=0.8`（与现状一致）、`llm_retry_backoff_429=2.0`。两条路径的循环与终止条件改为读配置。

**不动的红线**：流式已出字绝不重试；非瞬时错误立即抛；`reservation` 失败 cancel / 成功 complete 的两段式 token 语义不变。

**补充可观测性**：原实现重试过程**完全没有日志**，生产上"这次任务怎么慢了几秒"无从排查。两条路径在每次重试前补 `logger.info`（含退避时长、第几次/共几次、model、原因），手动验证时可直接在 backend 日志里数重试次数。

**测试**：`tests/test_llm.py` +8（29 passed）——状态码解析、429/500 可重试而 401/400 不可、429 退避基数更长、429 两次后成功且 `sleeps == [2.0, 4.0]`、500 重试成功、`llm_max_retries=0` 关闭重试、流式首块前 429 可重试且无重复输出。

## 4. p5.2 · DAG 层内子任务失败隔离

**问题**：`orchestrator.py` 的 `as_completed` 里直接 `fut.result()`，同层一个子任务抛异常 → **整层中断**，同层其余子任务即使已跑完，成果也一并丢弃。

**改法**（`orchestration/orchestrator.py`）：

- 新增 `_run_subtask_guarded()` 包住原 `_run_subtask`，串行与并行两条路径统一走它。
- 普通异常 → 转为 `AgentResult(hit_cap=True, final="子任务 X 执行失败：...")`，**继续执行同层其余子任务与后续层**；同时发 `error` 事件（`code=SUBTASK_FAILED`）并补发 `status=done`（否则前端该子任务的 Agent 徽章会一直停在 running）。
- **`RunCancelled` 原样上抛**：用户主动暂停不是失败，若被隔离吞成"某个子任务失败"就会继续往下跑，违背取消语义。
- 复用现有 `hit_cap` 语义而不是新增字段：`compose_subtask_text` 对 `hit_cap` 的分支本会标注「未完成」并提示"不要当作已完成的数据"（§四.5 失败不可伪装成结果），下游因此天然能感知，**无需改下游**。
- 返回仍按 `dag.subtasks` 顺序重建，确定性不变。

**测试**：`tests/test_orchestrator.py` +5（串行隔离、并行隔离且顺序确定、失败不阻断后续层且下游拿到 `hit_cap`、失败上游在子任务文本里被标「未完成」、取消仍上抛）。

## 5. p5.3 · 工具级重试退避生效

**问题**：`ToolRegistry.call` 缺省 `backoff=0.0`，重试是"失败后立即再打一次"，对 DB 连接抖动、对端限流这类需要短暂等待的瞬时错误基本无效。

**改法**：`backoff` 缺省改为 `None` → 读新增的 `settings.tool_retry_backoff`（缺省 0.3s）；显式传 `backoff=0` 仍可关闭退避，既有调用方与测试语义不变。**只改间隔、不改重试次数**，因此非幂等工具的副作用风险与现状完全一致。

**测试**：`tests/test_tools.py` +3（缺省读配置且 `sleeps == [0.5]`、退避随次数增长 `[0.2, 0.4]`、显式 `backoff=0` 不 sleep）。

## 6. p5.4 · checkpointer 可选 sqlite 持久化 + 真续跑

**问题**：`run_task` 每次 `MemorySaver()` 新建实例，存档随调用结束失去引用、进程重启即丢，续跑只能退化为 routes 的「按原请求从头重跑」，已完成节点重复执行、重复计费。

**先做探针再写实现**（这一步避免了线上静默事故）：

| 场景 | resume 行为 | 已完成的前置节点 |
| --- | --- | --- |
| `SqliteSaver`，换新实例（≈跨进程重启） | 真续跑 | **未重跑**（计数 1） |
| `MemorySaver` 换新实例 | **静默从头重跑，不报错** | 被重跑（计数 2） |

=> 对无存档的 thread 发 `Command(resume=True)`，LangGraph 不抛错而是静默重跑。生产上一旦持久化失效，就会退化成**重复执行、重复计费且零告警**。

**改法**：

- 新增 `orchestration/checkpoints.py`：`memory`（缺省）每次新建、严格保持现状；`sqlite` 进程级共享单例 + 落盘（`check_same_thread=False` + 锁，因为 `/tasks` 在 worker 线程跑）；未知后端 fail-closed 抛错。配套 `reset_checkpointer_for_tests()`。
- 新增配置 `checkpointer_backend=memory`、`checkpoint_sqlite_path=data/checkpoints.sqlite`。
- `graph.py` 的 `run_task` 改由 `get_checkpointer()` 取实例；`resume_task` 恢复为可用的真续跑，并**先 `get_state` 校验确有挂起点，否则明确抛错**，把持久化失效暴露在续跑之前而不是之后。
- 新增依赖 `langgraph-checkpoint-sqlite==3.1.2`（装入后 langgraph 仍为 1.2.16，未漂移）。

**为什么现在敢做真续跑**：当前唯一的 `interrupt()` 落在 `quota` 门——`set_entry_point("quota")`，位于 planner 之前、`reserve` 失败那一刻。恢复后只需重试一次 `reserve` 再进 planner，**该位置零副作用**，不需要为节点幂等做任何改造。挂起点恰好选在了最安全的位置。

**测试**：新增 `tests/test_checkpoints.py` 6 条——memory 每次新建（现状不变）、未知后端 fail-closed、sqlite 单例共享且落盘、**跨实例恢复且已完成节点不重跑**、无存档时 resume 抛错且计数器证明没有静默重跑、memory 新实例续跑被校验拦下。

## 7. 方案取舍与否掉项

- **不把 ReAct / DAG / 流式换成 LangGraph 的 `create_react_agent` / `Send` / `astream`**：会丢掉观察摘要化、护栏、逐步计量、双协议与前端事件契约，净损失。
- **memory 模式不做隐式共享**：共享虽能让同进程多次调用找回存档，但会改变历史行为并可能影响既有测试；缺省路径必须零变化。
- **HTTP `/tasks/{id}/resume` 本期不切换真续跑**：涉及事件流 seq/turn_id 续接与 `settle` 的 actual 口径变化，且只在 sqlite 模式下有意义；缺省 memory 下接入属于无收益改动。列入后续。
- **失败隔离不新增状态字段**：复用 `hit_cap`，下游零改动。
- **不改 `init.sql`、不加 DB 迁移**：sqlite 存档是新增独立文件，与业务库无关。

## 10. 后续

0. **接 sqlite 前必读：checkpointer 命名注意（2026-11-01 实测 langgraph 1.2.16）**
   - memory 侧：`class InMemorySaver` 才是正式定义（`checkpoint/memory.py:34`），`MemorySaver = InMemorySaver  # Kept for backwards compatibility`（同文件 `:634`）只是**兼容别名**，两者 `is` 同一对象，导入**不触发 DeprecationWarning**。
     => 现在代码用 `MemorySaver` 没错也没负担；看到官方文档推 `InMemorySaver` **不要当成需要适配的不兼容新 API**，它是同一个类，不要做无意义改名。
   - sqlite 侧**命名不对称**（这才是真正的坑）：同步是 `from langgraph.checkpoint.sqlite import SqliteSaver`，异步是 `from langgraph.checkpoint.sqlite.aio import AsyncSqliteSaver`，**没有 `InSqliteSaver` 这种变体**。本项目 `graph.invoke()` 同步调用 → 用同步 `SqliteSaver` + `check_same_thread=False`；若将来改 `astream`，必须换 `AsyncSqliteSaver`，同步版会阻塞事件循环。
   - postgres 侧：`PostgresSaver` / `AsyncPostgresSaver`，仅在 backend 多实例部署时评估（sqlite 多副本等于各写各的）。
   - 上述内容已写入 `app/orchestration/checkpoints.py` 模块头，改代码时可直接看到。
