# 迭代总结 · v1.0.0-p6.9 — 文档通读 + 打字机逐字感修复

> 用户两问：①文档读取是不是只能读 300 字？怎么通读整篇？②RAG 逐字打印明显，
> 这个项目为什么看不到——是文本合并优化牺牲了打字机吗？Tag：`v1.0.0-p6.9`。

## 1. 问题 1：文档读取的真实截断链路（不是 300 字）
给 LLM 的 observation 经**四层截断**（用户看到的"只覆盖开头"是它们叠加的结果）：
1. `read_document` 工具：`content[:max_chars]`，max_chars=8000（p5.2 定的）；
2. `_summarize_observation`：content 截 1200 字（p6.7 定的，修 p6.7 幻觉问题时收得过紧）；
3. **`brain._render_history`：`st.observation[:400]`**（p4.1 定的、一直没人动）——
   **真正的最后一层瓶颈**：LLM 每轮只看每个 observation 前 400 字；
4. 前端步骤面板展示 `[:500]`（纯展示）。

**修复（全部放大）**：
- `read_document` max_chars：8000 → **50000**（2 万字文档一次拿全）；
- `_summarize_observation` content 截断：1200 → **24000**（超 24000 才截并标注）；
- `_render_history` observation：400 → **24000**（真跑验证：LLM 答出文档**最后一章
  「十八、日志与可观测性」**——旧 400 字截断下绝不可能）；
- 前端 observation 展示：500 → 2000。
- 上下文容量评估：2 万字 ≈ 2 万 token，deepseek-chat 128K 装得下 3-4 轮；
  更大文档（>24000 字）仍会截断并如实标注——"分段读取"工具参数留后续。

## 2. 问题 2：打字机逐字感——不是后端合并，是前端渲染节流
**A/B 实测（数据说话）**：经 3001 网关 174 delta / 经 8080 nginx 88 delta，两者
**平均间隔都是 5ms 级**——后端→网关→nginx（已 proxy_buffering off）→前端，
流本身没有大块合并。
**真凶**：`MarkdownView` 流式期间 **80ms 渲染节流**（p6.3 加的，防每 delta 全量
重解析 markdown）——80ms 窗口合并 ~16 个 delta ≈ 80 字一次渲染，视觉"一段一段蹦"。
RAG 逐字明显是因为纯文本追加渲染（无 markdown 重解析节流）。
**修复**：**自适应节流**——短文本（<2000 字，绝大多数回答）**每 delta 直接渲染**
（真逐字，marked 解析 <1ms 撑得住）；长文本（≥2000 字）50ms 节流（timer 触发渲染
**最新文本**，用 ref 防旧快照）。

## 3. 顺手抓到的账务 bug（记入待修）
测试中发现钱包余额被打到 **-2493**：多轮大文档任务的实际用量超出 reserve 预扣，
`settle` 补差把余额**穿 0 成负**——两段式的原子性只保证预扣时刻，不防实际超支。
**待修**（p6.x）：settle 时余额下限保护（不足部分挂账/告警），或 reserve 估算按
上下文长度动态化。本轮测试钱包已充值 100000 恢复。
