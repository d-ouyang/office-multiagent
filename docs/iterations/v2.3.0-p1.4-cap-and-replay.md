# v2.3.0-p1.4 · 单步上限提到 5 万 + 回放缺表降级

> 2026-11-17 · 分支 `feature/2.3.0-context-budget` · pytest 593 → **594 passed / 3 skipped**

## 一、单步上限 24000 → 50000

### 事故

用户测第 3 题「读取 smoke-long2.md，第 10 章上限多少」，模型回答：

> 第 10 章正文在文件读取结果中被截断，未看到该章的"要点"限额…按前 9 章规律应为 200000 元
> ——此为推断，非原文确认。

行为本身是对的（如实标注推断，没有编造），但**数据能定位到根因**：

| 指标 | 值 | 含义 |
| ---- | -- | ---- |
| `budget` | 629,145 | 1M 窗口 × 60% |
| `used` | 4,304 | 只用了 0.7% |
| `dropped` | **0** | 预算器一次都没降级 |
| 文档字数 | 24,658 | |
| 单步上限 | 24,000 | **差 658 字，正好切掉第 10 章要点** |

也就是说：**这次截断跟预算器无关**，是 p6.9 时代为"2 万字通读"定的硬编码单步上限先卡住了。
现在有预算器兜总量，24K 的单步上限只会自我限制（1M 窗口用 24K 卡自己没道理）。

### 改动

`config.py`：`observation_max_chars` / `history_step_max_chars` 默认 24000 → **50000**，
与 `doc_read_max_chars` 齐平（5 万字以内一次读完）。

### 判据

同一问题重跑：**直接答「200000 元（20 万元）」**，回答里不再出现"截断/推断"。

### 边界（写清，避免下次误判）

- 超过 5 万字的文档**仍会截尾**——这是 `doc_read_max_chars` 的产品选择，不是 bug。
  真正的解法是分段读取（`PLAN-2.4.0` Phase B）。
- 多步大文档时，总量由预算器（窗口 × 60%）兜底，不会被单步上限放开搞爆。

## 二、回放缺表降级

### 事故

`GET /api/v1/runs/{id}/replay` 直接 **500**：

```
sqlalchemy.exc.ProgrammingError: (1146, "Table 'office.tool_invocation' doesn't exist")
```

本地 `alembic_version = 0013`，漏了 0014 迁移。**回放是排障工具，因为少一张表就把最有用的
`events` 一起挡在门外**——排障的人连事件都看不到，这比缺数据更糟。

### 改动

`api/runs_api.py`：新增 `_safe_rows()`，四处查询（invocations / call_log / usage / dead_letter）
缺表即降级为空列表 + WARNING 日志，返回体新增 `degraded: [...]` 标明哪块降级了。

### 判据

同一 run 回放：**200**，`degraded = ["tools.invocations"]`，`events = 416`（事件流完整保留）。

### 遗留

本地库仍停在 **0013**，意味着**幂等守卫（C1）在本地是空转的**（代码对缺表静默降级）。
要本地全功能验证，需执行：

```bash
docker exec office-multiagent-backend-1 alembic upgrade head
```

生产有该表，不受影响；新库部署时 `init.sql` 已含 `tool_invocation`，也不受影响。
