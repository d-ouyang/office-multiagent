# 意图识别方案（讨论稿）

> 状态：已按本文完成第一版改造（v1.0.0-p6.32）。后续用真实误判日志继续校准。
> 背景：关键词打分能测、便宜，但口语和追问都会误判。销售总结那次（run `074e6de7`）已经证明「词在句子里」不等于「用户要做这件事」。

---

## 1. 先把两件事分开

「看看上海卖得怎么样」**不是指代**。句子里没有「这个、那个、刚才、呢」。城市和问题都写全了。它识别不准，是因为 `planner.yaml` 的分析类关键词是「分析、统计、趋势、对比、占比……」，**卖得怎么样 / 看看**一个都没列。这是同义说法覆盖不住，和有没有上文无关。首轮这么问、上文在聊别的，结果一样：规则看不见这句是在问销售。

指代是另一类。用户说的是「那上海呢」「再出一份」「按这个画图」「刚才那个表加上退款」。离开上一轮，这句话自己不成立。

| | 例子 | 现在会怎样 |
| --- | --- | --- |
| 说法不在词表里 | 看看上海卖得怎么样 | 意图经常落空或只剩 `general`，复杂度分偏低，一个 Agent 硬做。Agent 自己有订单工具，有时仍能做对，但路由是碰运气 |
| 真·指代 / 省略 | 那上海呢；再导出；换成饼图 | 规划器只看本轮原文，看不到「上海相对谁」「导出的是哪张表」。回答模型后面能看见近期对话，但**路由已经定了** |
| 词撞上了但意思不对 | 文档里带一张图；记忆里出现「制度」 | 多记一个意图，分数过 3 就拆多 Agent。记忆污染那条已在 p6.30 用 `raw_text` 挡住 |

所以：**不是每句都先改写再识别。** 独立句直接识别。只有这句离开上文就不成立时，才先改写成独立问题，再对改写结果做意图识别。

---

## 2. 现在实际怎么走

一次提问在 `routes._stream_task` 里分成两份文本：

1. **`raw_text`**：用户这一句原文。`planner_node` 只用它跑意图、打分、拆 DAG（p6.30）。长期记忆、历史摘要、近期对话**不**进入规划器。原因是真实事故：记忆里的「财务制度」让「制度」命中知识库关键词，2.5 分的单 Agent 被抬成 4.5 分的多 Agent。
2. **`effective_text`**：`prepare_turn` 拼上历史摘要、最近 4 轮、长期记忆，再交给 Agent。若本句含「这个、那个、它、刚才、上面、这份、该表」等，再附一块提示：「只根据上面的对话确定指代，对不上就说不确定」。

指代提示只约束**回答和选工具**，不产生一个新问句，也不回头重跑规划器。知识库侧自己的多轮改写（`standalone_question`）也用不上：办公的 `rag_retrieve` 只把当前 `query` 发给 `POST /api/v1/qa/ask`，不带办公会话。

复杂度分仍是规则累加（`planner.yaml`）：连接词、多一个意图、多一种输出、超长、条件词。满 3 分走多 Agent。配置里的决策小模型 `decision-llm`（Qwen2.5-7B）还没接上。

## 3. 可借鉴的做法

不照搬整套对话平台（Rasa、Dialogflow、CLU、Lex）。那些是「意图 + 槽位」填表，要标注语料，和这里「选哪个办公 Agent、要不要拆开」不是同一题。下面四条是和本项目同形的参考。

### 3.1 知识库项目里的问题改写（直接可抄的边界）

`rag-qa-system` 的 `core/rag_chain.py`：

- 多轮时，先把依赖上文的追问改成**独立问题**，再检索。单轮默认不改写，省一次模型调用。
- 改写prompt只许输出问题，不许回答。
- `_sanitize_rewrite`：空、超长、像在作答（「根据公司规定……」），一律退回原句。改写失败只损失一点精度，把一段答案送去检索才是事故。
- `qa_cache.looks_anaphoric` / `is_standalone_question`：含「它、这个、上面、刚才、继续」或过短、以「呢」结尾，视为不能独立。这种句子禁止写进公共缓存。

办公的规划器应使用同一条纪律：**改写只补全指代，不回答；失败用原句；长期记忆不参与改写。**

### 3.2 对话式查询改写（Conversational Query Rewriting）

检索和客服里的标准步骤：用最近几轮对话把当前句补成不看历史也能懂的一句（CANARD 一类数据和后续的 T5 / LLM 改写都是这个任务）。改写结果叫 standalone question。意图、检索、路由都吃这一句，不吃拼起来的聊天记录。

### 3.3 结构化路由，而不是再堆关键词

OpenAI / Anthropic 的路由做法，以及本仓库已留的 `DecisionModel` 插槽：小模型在**封闭标签**里选，输出固定 JSON（意图列表、`single` 或 `multi`、一句理由）。不在标签内、JSON 不合法，就丢弃这次判断。

关键词继续负责一眼能确定的句子。拿不准才花这一次小模型。

### 3.4 不采用的

- **每句都做向量意图分类**（Semantic Router 一类）。6 个意图、没有标注句，近义句和「制度 / 分析」仍会混。等误判句子积累够了，可以给决策模型当例子，不必先上向量库。
- **把历史和长期记忆拼进关键词匹配。** p6.30 已经否掉。改写如果把整段记忆复述进新问句，等于把这个坑挖回来。
- **用回答用的大模型顺手做路由。** 贵，而且和后面 ReAct 重复。路由用已注册的 `decision-llm`。

## 4. 建议的流水线

```
本轮原文
  → 是否独立？
       独立 → 路由文本 = 原文
       不独立 → 决策小模型改写（只看最近 4 轮，不含长期记忆）
                消毒失败 → 路由文本 = 原文，并标明「指代未解开」
  → 规则打分（吃路由文本，仍不吃记忆块）
       清楚（单一意图、分数远离 3、无否定词）→ 采用规则
       含糊（多意图、分数在 2～4、有「不要/别/无需」、或刚改写过）
            → 决策小模型在封闭标签里选意图和 single/multi
            → 输出非法 → 退回「一个主意图 + 单 Agent」
  → Agent 仍看原文 + 近期对话 + 长期记忆
```

### 4.1 什么叫「不独立」

同时满足「有近期对话」和下面任一条，才改写：

- 现有指代词：`memory.py` 里的「这个、那个、它、刚才、上面、这份、该表」等。
- 补上知识库已经在用的：过短（规范化后少于 6 字）、「呢」结尾、「继续」。
- 省略追问：「上海呢」「再导出一份」「换成饼图」「按门店拆」。词表放 `planner.yaml`，和关键词一样可测。

「看看上海卖得怎么样」不含这些，**不改写**。它的问题在第 4.3 节，用决策模型补规则看不见的说法，而不是靠上文。

### 4.2 改写的输入和输出

- **输入**：最近 4 轮的问和答（与 `prepare_turn` 的近期窗口一致），加本轮原文。不要历史摘要全文，不要【用户长期记忆】。摘要和记忆里的「制度、手册」会再次劫持关键词。
- **输出**：一句独立问题。允许原样返回。
- **消毒**（对齐 `_sanitize_rewrite`）：空、比原句长出一截、含「无法回答 / 根据资料 / 抱歉」、明显在作答 → 退回原句。路由继续，但事件里写明未改写。
- **规划器**只看见消毒后的这一句。Agent 的任务文本保持今天的 `effective_text`，避免回答时丢了「用户到底怎么说的」。
- 过程面板分两行：`本轮原文` / `用于路由的句子`。两句不同才显示第二行，方便对误判。

### 4.3 意图和拆不拆

规则打分保留，作为快路径和回归测试的基线。决策模型只在含糊时介入，标签只能是现有 6 类加 `general`。

多 Agent 收紧，不再单靠「分数 ≥ 3」：

- 后一步要用的工具，前一个 Agent 的白名单里已经有（分析里带图表、带导出、带写文档）→ 保持单 Agent。这是 p6.30 折叠规则要推广的原则，不限可视化。
- 只有存在真实交接、且下一个 Agent 才有那项工具时才拆（先清洗上传表，再分析；先查制度口径，再写进报告）。
- 模型判断失败：退回规则给出的**主意图 + 单 Agent**。拆错会多跑一整段并重复计费；并进一个工具更全的 Agent，最多是这个 Agent 多叫一两个工具。

「看看上海卖得怎么样」走这条含糊分支：规则意图空或只有很弱的命中，决策模型应标 `analysis` + `single`。不需要改写。

### 4.4 和知识库检索的关系

办公侧规划器改写，是为了**选对 Agent**。知识库内部仍会对自己的 `query` 做多轮改写，但那次改写看不见办公对话。因此：

- 用户在办公里说「按刚才的制度再查一条」，规划器改写后的句子应作为 `rag_retrieve` 的 `query`，而不是只传「再查一条」。
- 不把办公的 `session_id` 传给知识库。`persist: false` 的约定不变。

## 5. 改造时不要做的

- 不把长期记忆、历史摘要拼回 `plan()` 的输入。
- 不让改写模型回答问题，也不把改写失败当成任务失败。
- 不为 6 个意图先做向量库或微调语料。规则和决策模型不一致的句子先记日志，够一批再考虑。
- 不把复杂度阈值从 3 改成一个更玄的公式来「修」误判。阈值解决不了同义说法和指代。

已知不一致：`planner.yaml` 写的是 `complex_threshold`，`router.py` 读的是 `complexity_threshold`（读不到就用默认 3.0）。改造时合成一个键，避免以后改了配置却不生效。

## 6. 验收（改造时用这些原句，不靠手感）

| 编号 | 输入 | 上文 | 期望 |
| --- | --- | --- | --- |
| A | 看看上海卖得怎么样 | 无 | 不改写；`analysis`；单 Agent |
| B | 那上海呢 | 上一句在问北京销售 | 改写含「上海」和销售；`analysis`；单 Agent |
| C | 再出一份，换成 pdf | 上一句是销售总结 docx | 改写能看出「销售总结 → pdf」；报告类；单 Agent |
| D | 查一下报销制度，再按这个口径算上海三月的实付 | 无 | 可不改写；知识库与分析都需要，且分析用得到检索结论 → 允许多 Agent |
| E | 拿到上海订单并写总结，文档里带趋势图 | 无 | 单 Agent（图表折进分析）。与 p6.30 相同 |
| F | 记忆里有「财务制度」，本句是「看看上海卖得怎么样」 | 长期记忆含制度 | 不进 `rag` |
| G | 这个呢 | 近期对话对不上任何对象 | 改写失败则用原句；不猜对象。Agent 按现有指代提示说不确定 |

A、E、F 必须仍能用规则测通，不依赖模型。B、C 的改写用决策模型，测试里可以注入固定改写结果，避免用例绑死在某次采样。

## 7. 建议的落地顺序

1. **独立句判定 + 改写插槽**（本文 4.1、4.2）。过程面板能看到原文和路由句。这是指代题的主体。
2. **含糊时才调用 `decision-llm` 做封闭分类**（4.3）。「看看上海卖得怎么样」在这一步解决。
3. **收紧多 Agent 条件**，并修正 `complex_threshold` / `complexity_threshold` 键名。
4. 日志里留下规则与模型不一致的句子，再决定要不要补关键词或例子。
